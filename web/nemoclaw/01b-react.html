The ReAct Loop

Observe, reason, act, repeat. Coined in the LLM context by Yao et al. (2022), who showed that interleaving reasoning steps with tool calls outperforms either reasoning alone or tool use alone on a range of tasks. The key property is that the model can update its plan after each observation: if a tool returns something unexpected, the next reasoning step incorporates that before deciding what to do next.

The signal is one field on every chat response: finish_reason. A six-line router reads it, the model picks a tool, your code runs it, the model reads the result, and this repeats until the model says done. Simple as it is, this loop is the core of most general-purpose agent frameworks; LangChain's createReactAgent, which this module uses later, is one. This page builds the four moving parts end-to-end and adds the safety belt that keeps it from running indefinitely.

The one field that tells the loop what to do next

Every chat-completions response carries a finish_reason field that tells you why the model stopped generating. Inside an agent loop this field is the only signal you need to decide what to do next: run a tool, return the answer to the user, or handle an error.

Two values cover the common branching:

  • "stop" means the model has written its final answer and the loop can exit, delivering content to the user.
  • "tool_calls" means the model is asking your code to run the named function and append the result before calling back.

There are also some values that may prompt fallback harnesses, retry loops, and human intervention. This might include:

  • "length", which fires when the model hits its token cap.
  • "content_filter", which fires when a safety classifier trips.

The four pieces every LLM agent is built from

There are typically four pieces needed to compose a modern LLM agent.

Keep in mind that each of these modules is independent. Swap the model, swap the tools, swap the router; the others should keep working IF they have stable contracts.

That independence also matters for how you read agent code you didn't write. Any LLM-based agent, however it is packaged, must contain these four pieces. When something breaks you can ask: is the model returning the wrong finish_reason? Is the messages array missing a turn? Is the tool executor returning an unexpected value? Is the router misreading the signal? The four-piece frame gives you a checklist that applies regardless of how the surrounding code is organized.

Building the loop from scratch with one tool

As an exercise, we can try to create a simple loop from scratch. All we need is one tool (get_current_time), one system prompt, and one while loop. Run it with "What time is it right now in UTC?" to start, and see what else you can ask:

  1. Step 1. The model asks for the tool.
  2. Tool run. The executor runs the function and appends the timestamp as a tool-role message.
  3. Step 2. The model reads the timestamp and writes the user-facing answer.
  4. Exit. The loop ends when finish_reason reads "stop".

Try both variants the canvas suggests. "What time is it right now in UTC?" routes through the tool, because the model genuinely does not know the answer. "What is the capital of France?" routes around the tool: the model knows Paris from training and skips the call entirely. The difference shows up in finish_reason on step 1.

What just happened inside the messages array.
The loop pushed four things into state.messages:
  • the system prompt (turn 0),
  • the user question (turn 1),
  • an assistant message with a tool_calls field (turn 2, the request),
  • and a tool-role message holding the function's return value (turn 3).
The second LLM call read all four, including the new tool result, and wrote the final answer.
The growing array is the only "memory" this agent has. If you saved that array to disk and reloaded it next week, the model would resume the conversation without noticing the gap.

Why the loop needs a step cap

Each step costs tokens and bloats the messages array. A confused agent (one that misreads its tool spec or gets stuck retrying) keeps going as long as the endpoint answers. MAX_STEPS = 6 is the cheap backstop: it caps total cost and forces you to think about what the right failure mode should be when the agent cannot converge.

Context rot, briefly. The messages array grows on every turn. After enough turns the original user request is buried in the middle of the array, and models tend to under-weight tokens stranded in the middle of a long context while favoring the beginning and the end. That effect is documented in "Lost in the Middle" (Liu et al., 2023). A 6-step cap is the cheap fix and does not solve the underlying problem. The structural mitigations each trade something away. Having the model plan ahead before it accumulates observations, delegating sub-tasks so each sub-agent works on a short context, or rolling earlier turns into a summary all cost latency, fidelity, or complexity, and each is worth evaluating against the task at hand. For now, MAX_STEPS is the dumb-but-effective backstop that keeps a confused agent from quietly spending far more than you intended.

The model decides which pages to read to answer your question.

What the cell produces is an artifact. Run it and you do not get a wall of logs: you get a working chat panel, rendered from the agent's own code, that you can talk to. The word predates the buzz; build pipelines have shipped "artifacts," and ML training has emitted "model artifacts," for years. Anthropic's recent live artifacts sharpened the idea for agents: a persistent, interactive HTML surface an agent builds and you keep using, not a one-shot answer. Before you continue

Each question is answerable by editing inputs in the canvas above and rerunning.

  1. Force the model to call the tool even when it does not need to. Try a question the tool genuinely cannot answer ("capital of France?") and watch finish_reason on step 1. Was it "stop" or "tool_calls"? Now edit the system prompt to require a tool call before answering ("You must always call get_current_time once, then answer."). Does the model comply? What does that tell you about how strongly the system prompt steers a model that has training-data confidence in another direction?
  2. Count the steps on a genuinely tool-needing question. "How many minutes until 17:00 UTC?" takes more than one tool call. Run it a few times. Did the model call get_current_time once, twice, or three times? Why would a model re-call a tool whose output it already has, and how would you discourage that in the system prompt?
  3. Make the safety belt smaller. Set MAX_STEPS to 2 and ask a question that would normally take 3 steps. The loop exits with no final answer. Will it do better next time? Will it show self-awareness and adapt to this harness limitation?
Module 1 closes here. You now have the two structural pieces an LLM-based agent is built from: a stateless chat-completions call and a loop that reads finish_reason to decide when to keep going. The remaining modules build on exactly this foundation; the core machinery does not change, but subsequent methods add structure to how the model communicates, widen the tool surface, and eventually compose multiple loops together.

References

  • Yao et al., ReAct: Synergizing Reasoning and Acting in Language Models (2022). The original alternating thought / action / observation pattern; the figure above is redrawn from this paper.
  • Wei et al., Chain-of-Thought Prompting (2022). The "reason" half of ReAct; what the model is doing inside reasoning_content when it deliberates before acting.
  • Xu et al., ReWOO: Decoupling Reasoning from Observations (2023). A deliberate contrast to ReAct: the model writes the whole plan up front and a separate executor runs it without re-querying the model between steps. Comparing the two reveals the trade-off between reactive replanning and pre-committed execution.
  • Schick et al., Toolformer (2023). Covered again in 1c's references; revisit here for the underlying mechanism the ReAct loop exploits.
