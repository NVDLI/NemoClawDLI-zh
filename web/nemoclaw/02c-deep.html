Deep Agents

A deep agent, sometimes called a research agent, is one that works on more than a single level at once. An orchestrator at the top takes a task, breaks it into smaller subtasks, and hands each one to a separate sub-agent that runs in its own fresh, isolated context, while a shared filesystem carries results back and forth between them. Reach for this pattern when one context can no longer hold the work, which tends to happen under any of the following conditions.

  • A task may be too large to fit in one context window.
  • Its subtasks may need to stay isolated so they cannot contaminate one another.
  • Its results may have to outlive a single run and persist as files on disk.

We build up to it in three steps. The first shows why a flat ReAct loop breaks down once a task runs long. The second introduces the four structural pillars that hold a deep agent together. The third wires LangGraph createReactAgent for the single-agent case and then hand-rolls the full version so that every step stays observable.

Where a single growing context breaks down

Every module so far has built single-context agents, a single ReAct loop driving one model through a steadily growing stack of tool calls, with everything the agent does landing in that same context.

That shape has three failure modes, and each one gets worse the longer a task runs:

  • Context overflow. The accumulated history plus tool results plus retrieved chunks crosses the model's context window, and tokens at the bottom of the array start to get dropped or compressed.
  • Context rot. Even within the window, tokens far from either end get under-weighted (Liu et al., "Lost in the Middle"). The agent forgets the original objective midway through.
  • Cross-task interference. Reasoning about subtask N pollutes the context the agent has for subtask N+1. Specialists running in dedicated, isolated contexts would each do better.

The deep agent fixes all three by splitting responsibility. A dedicated orchestrator writes a plan, then hands each subtask to a fresh sub-agent that sees only its own work.

Sub-agents exchange results through a shared filesystem, so one sub-agent's output reaches the next without routing back through the orchestrator's context window.

Each sub-agent's context holds only the plan and its one task, with none of the orchestrator's accumulated history. The sub-agents never share a context, so a final synthesis step reads the shared files and writes one combined report.

Topology comes from LangChain's "Deep Agents" framing (Bryk, Hwchase17 et al., 2025) and the NVIDIA AI-Q Blueprint; the four-pillar decomposition below maps directly to the deepagents npm package's public API.

The four pieces a deep agent is built from

Pillar 1 · Planning

A dedicated write_todos step runs before any execution begins, producing a structured list of subtasks. Writing the plan to shared memory first matters because it makes the decomposition inspectable and reusable: every sub-agent can read the same plan without the orchestrator having to re-explain the goal in each call.

Pillar 2 · Delegation

A task tool spawns a new sub-agent for each TODO item, and every one of them starts from a clean slate. None of the orchestrator's accumulated context reaches it, so no subtask can interfere with another.

Pillar 3 · Memory

A virtual filesystem, implemented here as a plain map from file paths to file contents, persists across all agent calls and is visible to every sub-agent. Without it, each fresh sub-agent would start blank; the filesystem preserves completed work across the context boundary from one sub-agent to the next.

Pillar 4 · Sandbox

Shell-grade work runs inside an isolated container boundary. A sub-agent that writes files or runs commands cannot reach the host from there. The browser exercises on this page run with no real shell available and fall back to the virtual filesystem as their sandbox. Inside a full NemoClaw launchable the openshell service supplies the real container boundary and executes commands on the agent's behalf.

  • Planning and Memory work together as a pair: the plan is written to the virtual filesystem once, and every sub-agent can read it from there without the orchestrator having to pass it explicitly.
  • Delegation and Sandbox work together as a pair: each spawned worker runs in an isolated execution surface, so a failure or runaway in one task cannot corrupt the context of another.
  • The NVIDIA AI-Q Blueprint is the production reference: same four pillars, typed task graph, durable state, human-in-the-loop approval as first-class graph state.

Pointing LangChain at whichever endpoint is active

ChatOpenAI is a model wrapper that speaks the OpenAI HTTP protocol. All that changes between environments is the baseURL it points at, whether that is https://integrate.api.nvidia.com/v1 on build.nvidia.com or any self-hosted NIM endpoint you choose to run instead. Everything downstream, including chains, graphs, and retrieval pipelines, is written once and works against any of those targets.

The node below calls helpers.getConfig(), which returns whichever endpoint is currently active. On build.nvidia.com that resolves to the NVIDIA API and uses your API key, while inside a NemoClaw launchable the same call resolves to the local model worker with no manual swap needed.

ChatOpenAI interface. The two methods you will use throughout the rest of this module are:
  • .invoke(messages) returns an AIMessage with the complete parsed reply. Use this when you need the full response before continuing.
  • .stream(messages) returns an AsyncIterable of partial messages, one chunk per token batch. Use this when you want to display output incrementally.
Both methods satisfy the LangChain Runnable interface. A ChatOpenAI instance can therefore drop into any spot that expects a Runnable. A chain slot, a LangGraph node, and the tail of a retrieval pipeline all accept it through that one shared interface and need no glue code.

Building the same ReAct loop as a LangGraph state graph

LangGraph models ReAct as a graph in which nodes decide or execute and edges loop. The cells on this page are JavaScript, where createReactAgent({llm, tools}) assembles that graph. (In Python, langchain.agents.create_agent(model, tools) exposes the same shape with a cleaner interface.)

It accepts either a model string like "openai:gpt-4o" or a BaseChatModel instance, and we pass our baseURL-configured ChatOpenAI as that second form. Either way, the result is a compiled StateGraph you can invoke, stream, or nest inside a larger graph.

A graph is worth the extra structure once the control flow outgrows a simple loop. Once the flow grows past "model decides, tool runs, repeat" a graph reads more clearly than a loop. The usual triggers for making the switch are these.
  • A human-approval gate before destructive tool calls.
  • A router that sends some messages to a different sub-graph.
  • A checkpointer that persists state across crashes.
  • Parallel branches that converge back into a single answer.
LangGraph's StateGraph exposes the typed channels the loop was passing implicitly so that every node now reads as a pure function of that state and every edge as a routing predicate the runtime follows. The shape matches the canvases you have been editing all course.
