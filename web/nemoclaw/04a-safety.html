The NemoClaw Sandbox

Prompt rules alone cannot contain an agent; the containment has to live in infrastructure that the model cannot talk its way past. Every NemoClaw launchable ships with OpenShell, a kernel-level sandbox that decides what the agent is allowed to do regardless of what its prompt says. This page walks the argument for that split, then runs the same OpenClaw prompt under two different policies and watches the blast radius change.

Why a sandbox, when you already have a system prompt

Two arguments anchor every containment system worth deploying:

  • Prompt-level rules are wishes, not controls. Telling an agent "do not exfiltrate secrets" depends on the model deciding to obey. Models can be deceived. Adversarial retrieved content, malicious tool output, or another agent in the loop can all cause a compliant model to act against its rules. Infrastructure containment denies by default at the kernel: if the model decides to disobey, the kernel refuses the operation. A blocked file access returns EACCES, a blocked syscall returns EPERM, regardless of what the model thinks it's doing.
  • Least authority is old engineering. Saltzer and Schroeder named the principle in 1975: each component gets only the privileges it needs. Rice's theorem (1953) says non-trivial semantic properties of a Turing-complete program are undecidable in general; an agent with a code-exec tool is a Turing-complete program. The honest move is to instrument the runtime, not to statically prove the model. The 1970s OS designers worked out this discipline, and we are reapplying their work to agents.
The OpenClaw / OpenShell split. OpenClaw is the agent runtime: it decides what to do given what's possible. OpenShell is the kernel-level sandbox that sits in front of it: it decides what's possible, by enforcing an explicit policy on every filesystem access, network connection, and syscall the agent attempts. Each piece is small and testable; neither tries to do the other's job. The kernel sandbox runs as a supervisor in front of every action the OpenClaw runtime would take.

Four mechanisms OpenShell composes

OpenShell enforces its policy through four kernel-level mechanisms. None of them is novel; the value is in using all four together with one policy file as the single source of truth.

1 · Network namespace

The agent's process runs in its own netns with no outbound access by default, so you have to allowlist destinations explicitly.

2 · Landlock

Filesystem capability dropping at the kernel. The agent literally cannot open files outside the workspace tree. No bind-mount tricks, no symlink races.

3 · seccomp

A per-process syscall allowlist applied at the BPF layer. Any syscall outside the allowlist (ptrace, mount, setuid, and similar) returns EPERM before the kernel even begins to execute it, so there is no race between inspection and enforcement.

4 · OPA-evaluated CONNECT proxy

The only egress route. Policy-as-data decides which hosts and ports the agent's outbound TCP connections may reach. The rules live in a file you edit, not in the agent.

Step 2 · The gateway is the control plane

The gateway you drove in 03a is not a convenience layer over the agent. It is the agent's entire admin surface. Every mountClawGateway call you made (list models, list crons, chat) authenticated with one secret: OPENCLAW_GATEWAY_TOKEN. That single token carries operator.admin scope.

Whoever holds that token can do far more than chat. They can rewrite who the agent is and what it does on a schedule:

  • agents.files.get pulls SOUL.md, the agent's persona and standing instructions, straight off disk.
  • cron.add plants a persistent job that fires long after the conversation ends.
  • A mid-task chat.send injection redirects the agent toward the attacker's goal while it still looks like it is working on yours.

None of this trips the sandbox. The OpenShell policy you just read governs the agent's outbound network and filesystem reach, so it constrains the actions the agent takes. The gateway sits above that boundary. It edits the agent's identity and task queue before any sandboxed action runs.

Key insight: the sandbox defends against what the agent tries to do. The gateway controls what the agent is. Read access to SOUL.md and write access to crons rewrite the agent upstream of every rule the sandbox enforces.

Step 3 · Three failure modes worth naming

The sandbox stops most of what people worry about. It is not the whole story. Three failure modes overlap with infrastructure controls in interesting ways:

  • SOUL.md supply-chain tamper · An attacker who gets a write into the agent's workspace can rewrite its persona. The sandbox can't catch this through introspection because the agent still passes its own prompt-level rules; the rules just changed. The mitigation is at the supply-chain layer: signed workspace contents, read-only base persona, rotation on tamper.
  • The lethal trifecta · Untrusted input, access to secrets, and a way to send data out. Each is fine in isolation. The composition is the bug, because the untrusted input can steer the agent into reading a secret and pushing it through the outbound channel. Either deny the composition at the policy layer, or split the agent into two with no shared session.
  • Peer preservation · An agent grading another agent on the same model shifts its verdicts in social context: a verdict it holds firmly in isolation can flip once a peer's name is attached to the output. No infrastructure control catches this; it is an application-layer failure mode. The fix is to use a stronger model as judge than as generator.
Defence comes in layers. Infrastructure, application logic, and behavioural monitoring each catch a class of failures the others cannot see. The sandbox stops kernel-level escapes, guardrails catch policy violations above the kernel, and monitoring catches the behaviours that look correct until you measure them.
