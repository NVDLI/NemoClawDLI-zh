Going Further

The modules so far built the loop from first principles. The natural next question is how to run it against your own data, your own users, and the constraints specific to your deployment. This page collects the concrete next steps: real infrastructure options, tools for bringing in your own knowledge, and the open problems worth pushing on once the basics are solid.

Deploy what you built

Moving the exercises onto a real runtime

The in-browser exercises were sized for learning: short-lived sessions, proxied endpoints, no persistent state. Moving from that to something you can actually ship means choosing a runtime that handles GPU provisioning, model serving, and long-running sessions. Two paths cover the range of cases you are likely to encounter.

NVIDIA Brev launchables

One-click GPU environments preloaded with the runtime components you saw in your launchable. Pre-built launchables exist for the LangChain deep-agents stack, OpenClaw-style file-as-context runtimes, and NemoClaw with kernel-level containment. The launchable handles GPU provisioning, the model server, and a Jupyter front end; you bring the repo.

OpenAI-compatible endpoints for every NVIDIA-hosted model. The Python and JS examples in this course paste in here unchanged; swap the baseURL from your launchable's proxy to https://integrate.api.nvidia.com/v1 and supply an NVIDIA API key. Free credits cover the experimentation phase.

Add new knowledge

Bringing your data in

The Index Agent in Module 2b ran against a small in-page corpus. A production deployment immediately needs four answers: what the corpus is, who maintains it, how it stays fresh, and how to measure the agent's accuracy on it. Three NVIDIA pieces address each part.

NeMo Retriever

The production successor to the cosine similarity retrieval from Module 2b. Sparse keyword search and dense vector search run in parallel and their scores are merged, a reranker re-orders the candidates by relevance, and configurable chunking primitives let you control how documents are split before indexing. Pair with NIM-served embeddings for a fully on-prem retrieval stack that keeps data inside your VPC.

NeMo Retriever →

NVIDIA AI Blueprints

Reference implementations for common agent shapes: a RAG chatbot, a multimodal PDF extractor, a research assistant. Each blueprint is the Research Agent (2c) configuration for one domain, fully deployable. Useful both as starting templates and as a sanity check on your own architecture.

AI Blueprints →

NeMo Data Curator

Bringing your own corpus in cleanly is itself a project. NeMo Data Curator handles deduplication, language filtering, PII removal, and exact-match scoring at the scales where doing it by hand stops working. Retrieval quality compounds on data quality, so cleaning the corpus once pays off across every query the agent ever makes against it.

NeMo Curator →

NeMo Guardrails

Programmable input/output filters, topic policies, and fact-checks that run at the application layer, above the model. NeMo Guardrails is the complement to kernel containment rather than a replacement for it: the two layers catch different failure classes, and you need both because neither covers what the other misses.

Where to push next

Three axes the agent vocabulary opens up

Production work pushes on three independent axes. Use the vocabulary from this course for each:

  • The knowledge layer. Production-grade retrieval: structural chunking, page-image retrieval, faithfulness eval on real heterogeneous corpora. NeMo Retriever and the RAG AI Blueprints are where this gets built for real.
  • The substrate. Wire-format protocols (MCP, the Responses API, OTel GenAI conventions, A2A) that keep tool capabilities portable across providers and frameworks.
  • Fleet dynamics and containment. What changes when N agents run in parallel: each agent redundantly re-discovers the same context (rediscovery cost), topologies with too many hops lose coherence, and an agent grading a peer's output can shift its verdicts based on social context rather than content. How to bound any single agent in the fleet with kernel-level containment (Landlock, seccomp, network namespaces) when prompt rules and guardrails are not enough to limit blast radius.

Pick the axis that matches the problem your current project keeps running into. The NVIDIA Developer Blog tracks the latest reference work on all three.

Three patterns worth carrying

What to remember when you ship one of these

Forecasts about agent productivity are systematically wrong.

METR's randomised trial of experienced open-source developers found a meaningful slowdown when using a coding agent, despite a forecast speedup and a self-reported speedup after the fact. The forecast-vs-reality gap is the finding. Plan for it when scoping the value of any agent you ship.

A single strong agent is the default.

The empirical pattern from published multi-agent work is that a single strong agent beats a multi-agent system past a threshold of task complexity, and that emergent behaviours at higher N can be worse than the failure modes you were trying to solve in the first place. Before adding an agent to the topology, name the specific failure mode that the extra agent is meant to fix. If you can't name it, the additional complexity is unlikely to help.

Kernel containment is the answer to "what survives a successful prompt injection."

Prompt rules and application guardrails help, but they cannot catch what they cannot see, and an injected instruction that looks valid to the model will pass through them. Every agent that touches a real shell, a real filesystem, or a real network needs a layer that does not read the prompt at all: one that enforces its rules at the syscall boundary regardless of what the model decided to do.
