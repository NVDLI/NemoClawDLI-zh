The Agent

An agent is an entity that interacts with an environment at any meaningful level. A person going about their day is an agent in this sense, and so is a thermostat holding a room at temperature or a self-driving car making its way through traffic.

All of them perceive their environment through sensors and act on it through actuators. Because each action feeds the next observation, perceiving and acting fold into one continuous cycle that lasts as long as the agent is working toward something. This course calls that cycle the perceive-reason-act loop. The agents you will build run the same cycle a thermostat does and are set apart only by how much they can perceive and how far their actions reach.

The three parts on the loop

A single trip around the loop runs through three parts, each with a plain name and a distinct job.

  • Perception gives the agent everything it knows about its environment. A thermostat reads a single number, the current temperature; a self-driving car fuses cameras, radar, and a map into a model of the road. Whatever perception captures is all the agent has to work from, since nothing downstream ever touches the world directly. A gap in perception becomes a gap the rest of the agent cannot see around.
  • Reasoning turns a perception into a decision, which can vary widely between agents. A thermostat compares the temperature against a target and stops there, while a chess engine searches millions of moves and a self-driving car runs a learned policy. The agents you build here reason by calling a language model, and almost everything the course adds later (tools/memory/planning) hangs off this single step.
  • Action changes the environment for itself and other participants. An action can be as small as flipping a relay or as involved as steering a car or calling a tool. It also marks the outer edge of an agent's reach, because however sharp the reasoning, the agent affects the world only through its action space.
The reasoning step is a pluggable socket. Perception and action do not care what sits between them. Anything from a simple rule to a decision tree to a full neural network can fill the slot without changing the loop around it. Building the loop once as a fixed frame and reusing it keeps two questions cleanly apart: how capable the reasoning is, and how far the actions reach.

That swappable socket is the seam along which the classic agent designs differ. Russell and Norvig's Artificial Intelligence: A Modern Approach lays them out as a spectrum, from a bare reflex agent up to a learning agent that improves its own rules. The agents you build here start at the reflex end, and dropping a language model into the socket carries them toward the later designs.

Two things worth examining in the code above:

  • The environment (wall positions, current position) lives in state.env, while the agent's intrinsics (its direction) live in state.agent. Keeping them separate means a different agent with different intrinsic state can operate in the same environment cleanly.
  • The reasoning step is one if statement. Replacing it with something more powerful, whether a decision tree, a neural network, or a language model, only requires changing what sits between perception and action. The loop structure, the state layout, and the action step all remain identical.

What changes when the socket holds an LLM

You call the chat-completions interface like any other function: hand it a list of messages and a model name, and it hands back one assistant message plus metadata.

About chat(). It is the course-provided wrapper you run live a little further down this page. The snippet below previews its call shape and the fields it returns, so the names are familiar by the time you reach the runnable cell. 
const reply = await chat({
  model:    "nvidia/nemotron-3-nano-30b-a3b",
  messages: [{ role: "user", content: "Hi" }],
});
// reply.choices[0].message  → { content, reasoning_content }
// reply.choices[0].finish_reason → "stop" | "tool_calls" | "length"

Three facts about that function shape how agents built on top of it have to work:

  • Calls do not share state. Between requests the server holds nothing for you. If you want the model to remember the previous turn, you send that turn again. The "memory" of a conversation is a list of messages your code maintains and re-sends each time.
  • The output has two channels. Reasoning models return their working notes in reasoning_content and their final answer in content. You inspect those working notes during development, while the next stage of the loop reads and acts on the answer in content.
  • finish_reason is the loop's exit condition. "stop" means the model has written its final answer. "tool_calls" means it wants your code to run a named function and report the result back. "length" means the token budget ran out before the model finished. A loop that drives an LLM-based agent is built entirely around reading this one field and deciding what to do next.

This course uses the Chat Completions API throughout: you keep the conversation as a messages[] array in your own code and resend the full array on every turn. The newer Responses API can hold the thread server-side instead, so you send only the new input and a reference to the prior turn. Either way the model stays stateless and unchanged between calls. The conversation lives outside it, in state your code or the server keeps.

What chat() actually sends

chat() is a convenience wrapper around one ordinary HTTP POST in the OpenAI-compatible wire format. That request carries three things:

  • the endpoint to send to,
  • an Authorization header carrying your key,
  • and a JSON body with model and messages.

The cell below makes that call by hand and shows both sides. Open request to see what leaves your browser with the key redacted, and raw response to see the full object chat() hands back.

Every endpoint in this course speaks this same format, including the OpenClaw agent runtime in Module 3.

Two things that call is quietly doing, and why. Neither is magic, and both are worth understanding before you trust them.
  • It goes through a proxy. The request does not hit build.nvidia.com directly, because a browser cannot: that endpoint does not return the cross-origin (CORS) headers a browser fetch requires, so the call is routed through a small pass-through proxy that adds them. The same proxy carries an X-BILLING-SOURCE: dli-nemoclaw-web header the course attaches to every request, so the usage is billed to this course rather than to a personal account. Your key is not hidden or swapped: it rides the same request straight to NVIDIA over TLS and is never stored anywhere but your own browser.
  • Streaming is wrapped in a helper. chatStream() is the same POST with stream: true, but the reply comes back as a Server-Sent-Events feed: many data: frames, a split between the answer and the model's reasoning_content, a closing usage frame, and a [DONE] marker. The helper parses that, routes the two channels to the panel, retries a dropped connection before the first token arrives, and honours the Stop button, so a cell can stay about the lesson instead of the SSE plumbing. It is not a black box either: open any cell's helper menu to read the exact source of chat, chatStream, and every other helper.

Swapping the reasoning step while the loop stays fixed

You now have both halves of an agent, and the stateless chat() function above will pair nicely with the previous reflex agent's perceive-reason-act loop. Before wiring the model into that loop, it helps to watch the reasoning slot accept brains that are not language models first.

Run the nodes in order. Each swaps a different brain into the same maze-solving loop:

  • The constant "always east" rule reaches the goal on a straight corridor, then stalls at the first wall in the maze, since a fixed heading cannot turn.
  • DFS dives and backtracks out of dead ends.
  • BFS fans out in rings before walking the shortest path.
  • A* biases those same rings toward the goal.
The reasoning slot is the only part that varies. DFS, BFS, and A* are mechanical fillers, dropped into the same slot to prove it accepts any brain that reads state and returns a move. The last node makes that literal: one line chooses the brain, and the steps below it run the same way whatever you chose. The chat() call you just ran is one more brain for that slot. It changes only two things. Perception now reaches the brain as text, and the brain's answer comes back as an intent signal your code applies. The next section zooms in on those two edges.

Putting a language model in the reasoning step to solve the maze

Drop a language model into the reasoning slot and the policy stops living in your code. It now lives in the fixed model weights and the prompt you feed them. Perception renders the maze as an ASCII map that becomes the user message, and the model's tool call to move stands in for the action while everything else carries over unchanged.

Run the engine node first; it exports the maze utilities and one shared solver (state.runMaze) that walks corridors automatically and calls the model only at junctions. Then pick a route:

  • the non-vision route sends the model only the ASCII map,
  • the vision route also attaches a rendered picture of the same maze.

Comparing the two routes shows whether a second modality helps; the ASCII text alone may already carry everything the model needs. Both runs hand you the same panel of controls, each one isolating a different variable:

  • the model selector swaps the brain driving the run;
  • the includeText, includeImage, and includeHistory switches decide what the model is shown;
  • the editable system DIRECTIVE rewrites the instructions it works under;
  • and the ADVANCED toggle grows the maze into a harder test.
A schema turns the answer into a typed action. The constant rule returned a string; BFS handed back a list. choose_direction gives the model the same contract but enforces it through a JSON Schema, so the loop reads a typed value instead of parsing free prose. With it, a language model can take the reasoning slot that BFS and A* held a moment ago.

The loop, drawn locally

Place the chat() call inside the loop that re-sends history, and a single turn of any LLM agent in this course takes the same four-stage shape. Name the stages now, because every security and reliability question later traces back to one of these four arrows.

  • Locally-sample. Your code reads a slice of the environment, which might be the maze cell and its valid moves, or the latest user message, or the contents of a file. It never reaches for the whole world at once, because all the turn requires is the narrow piece of state the model needs to act on this time around.
  • Locally-perceive. That slice is rendered into a full engineered context: the system prompt, the running messages[] history, prior tool results, and the slice you just sampled. All of it is plain text. For an LLM agent, perception is context engineering.
  • Locally-act. The model maps that text to more text: an intent signal, ideally a typed tool call like { "move": "east" } rather than free prose. The intent only requests an action, and it never performs one. Your code reads it and applies one bounded update to the environment (doMove(...)), validating it first.
  • Locally-impact. The update changes the world. Nothing persisted inside the model; the only durable state is the environment and the context your code will rebuild. The next turn's locally-sample reads the changed world, and the cycle repeats.

Look closely at the middle of that list. The perceive-to-act step is a single stateless text-to-text mapping in which a full engineered context goes in and an intent signal comes back. The model only transforms text, so perceiving the world and turning an intent into a real change remain your code's job on both sides of that mapping.

That leaves the green box below as the only piece you did not write. An agent therefore has just two choices: what you feed into its context, and what you do with the intent it returns.

Each pass of the loop acts only locally. The model reads one small piece of the world such as a single maze cell and hands back one bounded action before the stateless text-to-text step between them forgets everything it just saw. An agent that accomplishes a great deal is only this modest cycle repeated many times while the environment carries the state forward from one pass to the next. Module 1b builds that cycle in code where you can watch the context grow with each turn.

Before you continue

Each question is answerable by editing a knob in the LLM-maze cell above and rerunning it.

  1. Take the text away from the multimodal model. In the vision route, set includeText:false and leave includeImage:true, then rerun. The omni model now sees only the rendered picture of the maze. Does it still reach the goal, and does it take more decisions than the text-plus-image run did?
  2. Remove the strategy hint from the DIRECTIVE. Delete the line that says to prefer unvisited branches over visited cells, then rerun the non-vision route. Count the decisions against the run with the hint in place. How much of the model's competence came from that one sentence?
  3. Swap the brain in the slot. Change model:"omni" to model:"super" in the non-vision route and rerun. The loop, the maze, perception, and action do not change; only the reasoning socket does. Does the larger text model reach the goal in fewer decisions?
