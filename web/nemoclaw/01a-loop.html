The Agent

An agent is a loop. It reads its environment, decides what to do, acts, and comes back around to read again. That cycle is the whole shape, and it does not change from one agent to the next. What changes is a single step inside it: the rule that turns a reading into a decision. This page builds the loop with no language model anywhere in it, so every moving part stays visible, then drops a model into that one step and shows exactly what it takes over.

The shape under everything

Strip the labels off and every agent runs the same three parts on that loop, whether it is a thermostat or a self-driving car:

  • Perception turns the world into something the next step can use. For a thermostat that is a single number, the current temperature; for a driving system it is a fused readout from cameras, radar, and a map. Perception sets the ceiling on what the agent can know, because the reasoning step never touches the world directly, only this reading of it.
  • Reasoning turns that reading into a decision, and it is the only part that meaningfully differs between agents. A thermostat compares the temperature against a setpoint. A self-driving car runs a learned policy over its sensor readout. The agents you build in this course hand the reading to a language model. Everything this course teaches lives in this one step.
  • Action changes the environment, which produces the next perception and closes the loop. The thermostat flips a relay; the car turns the wheel; an LLM agent calls a tool. Action is also where an agent's reach ends, since it can affect the world only through the actions you hand it.
The reasoning step is a pluggable socket. The perception step and the action step do not care what sits between them. Swap the reasoning step for a rule, a decision tree, a neural network, or an LLM and the outer loop does not have to change. That substitutability is what makes the loop a useful abstraction. The hard questions, like how smart the reasoning is and how broad the actions are, stay separate from the question of how the loop itself is wired.

An agent with no language model

The reasoning step is a pluggable socket. The smallest plug is a single if statement. The environment here is a one-dimensional track with walls at positions 0 and 9. Press Run and watch the position number bounce.

Two things worth examining in the code above:

  • The environment (wall positions, current position) lives in state.env; the agent's intrinsics (its direction) live in state.agent. Keeping them separate means a different agent with different intrinsic state can operate in the same environment without either one leaking into the other.
  • The reasoning step is one if statement. Replacing it with something more powerful, whether a decision tree, a neural network, or a language model, only requires changing what sits between perception and action. The loop structure, the state layout, and the action step all remain identical, which is why the loop is worth writing once and reusing.

What changes when the socket holds an LLM

The chat-completions interface is also a regular function. You hand it a list of messages and a model name; it hands back one assistant message plus metadata.

const reply = await chat({
  model:    "nvidia/nemotron-3-nano-30b-a3b",
  messages: [{ role: "user", content: "Hi" }],
});
// reply.choices[0].message  → { content, reasoning_content }
// reply.choices[0].finish_reason → "stop" | "tool_calls" | "length"

Three facts about that function shape how agents built on top of it have to work:

  • Calls do not share state. The server is not holding context between requests. If you want the model to remember the previous turn, you send the previous turn again. The "memory" of a conversation is a list of messages your code maintains and re-sends each time.
  • The output has two channels. Reasoning models return their working notes in reasoning_content and their final answer in content. The notes are for you to inspect during development; the answer in content is what the next stage of the loop reads and acts on.
  • finish_reason is the loop's exit condition. "stop" means the model has written its final answer. "tool_calls" means it wants your code to run a named function and report the result back. "length" means the token budget ran out before the model finished. A loop that drives an LLM-based agent is built entirely around reading this one field and deciding what to do next.

If you have reached for the newer Responses API, this is the same picture. It keeps the conversation server-side, so you send a short reference instead of the whole messages[] on each turn, but the call underneath is still this stateless function: the model receives the full context and returns one turn. The convenience changes; the shape does not.

Swapping the reasoning step while the loop stays fixed

You now have both halves: the stateless chat() function above, and the reflex agent's perceive-reason-act loop from the top of the page. Before wiring the model into that loop, it helps to see the slot accept brains that are not language models, so the loop's independence from the brain is concrete. A one-dimensional track is too simple to make that point: the single rule "always head for the far wall" already solves it, so swapping brains changes nothing you can see. Two dimensions break that rule. A generated maze has dead ends and forks, and a fixed heading just marches into a wall and stalls. Solving the maze is not what this canvas is for. Watch what holds still instead: the maze, the perception step (validMoves), and the action step (doMove) all stay fixed while you drop a different brain into the slot between them. Run the nodes in order: the first animates a constant "always east" rule on a straight corridor (works) and on the maze (stalls) side by side; then DFS dives and backtracks out of dead ends; BFS fans out in rings before walking the shortest path; A* biases those rings toward the goal. Only the brain changes.

The reasoning slot is the only part that varies. DFS, BFS, and A* are mechanical fillers, dropped into the same slot to prove it accepts any brain that reads state and returns a move. The last node makes that literal: one line chooses the brain, and everything below it (perceive, act, loop) runs the same way whatever you chose. The chat() call you just ran is one more brain for that slot. All it changes is how perception reaches the brain, now as text, and how its answer turns into a move, now an intent signal your code applies. The next section zooms in on those two edges.

Putting a language model in the reasoning step to solve the maze

DFS, BFS, and A* read the maze as coordinates and carried their policy in code. Drop a language model into the same slot and the policy moves out of the code and into the prompt: perception renders the maze as an ASCII map, the map becomes the user message, and the model's tool call is the action. The loop, the maze, perception, and action are exactly what the search brains used. The only swap is the brain itself, now a language model, and that swap is what the rest of the course builds on.

Run the engine node first; it exports the maze utilities and one shared solver (state.runMaze) that walks corridors automatically and calls the model only at junctions. Then pick a route. The non-vision route sends the model only the ASCII map; the vision route also attaches a rendered picture of the same maze, so you can test whether a second modality actually helps or whether the text already said everything. Both routes expose the same controls: which model drives the run, the includeText / includeImage / includeHistory switches, the editable system DIRECTIVE, and an ADVANCED toggle for a larger maze. Flip them and watch how modality, context, and the model choice each move the result.

The tool call is the action interface. The constant rule returned a string; BFS returned a list. choose_direction gives the model the same contract but enforces it through a JSON Schema, so the loop reads a typed value instead of parsing free prose. That single rule, text in and a typed intent out, is what lets a language model take the reasoning slot that BFS and A* held a moment ago.

The loop, drawn locally

Set the stateless chat() function inside the loop that re-sends history, and a single turn of any LLM agent in this course takes the same four-stage shape. The stages are worth naming, because every security and reliability question later is really a question about one of these four arrows.

  • Locally-sample. Your code reads a slice of the environment: the maze cell and its valid moves, the latest user message, the contents of a file. Not the whole world, just what this turn needs.
  • Locally-perceive. That slice is rendered into a full engineered context: the system prompt, the running messages[] history, prior tool results, and the slice you just sampled. All of it is plain text. For an LLM agent, perception is context engineering.
  • Locally-act. The model maps that text to more text: an intent signal, ideally a typed tool call like { "move": "east" } rather than free prose. That intent is a request to act, not the act itself. Your code reads it and applies one bounded update to the environment (doMove(...)), validating it first.
  • Locally-impact. The update changes the world. Nothing persisted inside the model; the only durable state is the environment and the context your code will rebuild. The next turn's locally-sample reads the changed world, and the cycle repeats.

The middle is the part to stare at: locally-perceive → locally-act is a single stateless text-to-text mapping. A full engineered context goes in; an intent signal comes out. The model only transforms text; perceiving the world and acting on it stay your code's job, on either side of that one mapping. That is why the green box below is the only piece you did not write, and why control over an agent is control over what enters the context and what leaves as intent.

Why "locally". Each arrow is local in space and in time. The sample is a slice, not the whole environment; the impact is one bounded update, not arbitrary power; and the text-to-text mapping in the middle carries no state of its own across turns. An agent that looks like it is "doing a lot" is just this small local loop, run again and again, with the environment carrying everything forward between turns. Module 1b builds exactly this cycle in code and lets you watch the context grow on every pass.

Before you continue

Each question is answerable by editing a knob in the LLM-maze cell above and rerunning it.

  1. Take the text away from the multimodal model. In the vision route, set includeText:false and leave includeImage:true, then rerun. The omni model now sees only the rendered picture of the maze. Does it still reach the goal, and does it take more decisions than the text-plus-image run did?
  2. Remove the strategy hint from the DIRECTIVE. Delete the line that says to prefer unvisited branches over visited cells, then rerun the non-vision route. Count the decisions against the run with the hint in place. How much of the model's competence came from that one sentence?
  3. Swap the brain in the slot. Change model:"omni" to model:"super" in the non-vision route and rerun. The loop, the maze, perception, and action do not change; only the reasoning socket does. Does the larger text model reach the goal in fewer decisions?
