Modern CLI Agents

Four modern CLIs run agents from the command line. Each one wires the same five pieces together, and what separates them is the defaults they pick rather than the underlying shape. This page lays the four most influential CLI agents next to OpenClaw and points at which one to reach for given the work you have.

Four CLIs, in their own terms

Claude Code (Anthropic)

The CLI running in this very environment. Its beacon is CLAUDE.md at the project root, joined by ~/.claude/CLAUDE.md for user-wide directives. The tool palette is rich, covering file edit, bash, web search, sub-agents, and long-running tasks, and hooks let you intercept tool calls. Defaults stay conservative, so you opt into broader file and network access.

Codex CLI (OpenAI)

The same shape with a separate vocabulary. Its beacon is AGENTS.md, and the default sandbox is "approval mode," where every write or shell command waits for your nod unless you pass --full-auto to run it autonomously. The tool palette centres on shell, and even file-edit is implemented as shell.

Cursor / Continue (IDE-resident)

The same primitives, except the agent is wired through your editor. Beacons are .cursor/rules/*.mdc (the legacy single-file .cursorrules still works) or .continue/config.yaml, and the tool palette is editor-shaped around moves like "apply this diff to file X." Sessions sit in your editor's project state, and the sandbox is whatever your editor and OS happen to give you.

OpenClaw (NVIDIA NemoClaw)

The one you've been using. Its beacon is the whole workspace/ folder, where SOUL.md, AGENTS.md, IDENTITY.md, and the rest each surface a different slice of the system prompt. The tool palette runs inside a kernel-level sandbox you can hot-reload, sessions live server-side, and it is the only one of the four built explicitly for unattended operation.

The same pattern, in their own vocabulary

The pattern is older than the LLM. Developer tools have long read config from a file at the project root, layered it on top of a per-user config in your home directory, and gated side effects through a separate authorisation step. The main thing the agent shape adds is that the body of the request to the side effect comes from a model rather than from your keyboard.

Which one to reach for

The right choice depends on what you trust the agent to do unsupervised and how much friction you want on each action. A rough heuristic:

  • Claude Code for interactive work in a real repository where the agent is your pair, with a stable tool palette, good hooks, and fast iteration.
  • Codex CLI for shell-heavy work where you want explicit approval on every command, since approval mode is the right default for one-off operations on systems you don't fully trust the agent on.
  • Cursor for inline edits inside an existing codebase. The IDE integration is the value; the agent surface is intentionally smaller than the others.
  • OpenClaw for unattended deployment: cron jobs, scheduled audits, groups of co-operating agents running in parallel (fleet topology), anything that runs without a human in the loop. The kernel sandbox is what makes unattended operation safe, because each agent's syscalls are gated by a policy regardless of what the model decides to do.

A worked comparison

The same task, namely read oncall.yaml, find next Tuesday's on-call, and write a one-line summary to handoff.md, in each CLI's syntax.

# Claude Code
$ claude   # interactive; type the prose
> Read oncall.yaml, find next Tuesday's on-call, write a one-line
> summary to handoff.md.

# Codex CLI (approval mode)
$ codex
> Read oncall.yaml...        # asks before each edit

# Cursor (in-editor)
Ctrl-K → "read oncall.yaml, write a one-line summary to handoff.md"

# OpenClaw (HTTP)
$ curl -X POST $GATEWAY/v1/chat/completions \
    -H "Authorization: Bearer $TOKEN" \
    -H "x-openclaw-session-key: handoff-$(date +%F)" \
    -d '{ "model":"openclaw","messages":[{"role":"user",
          "content":"Read oncall.yaml, find next Tuesday'\''s on-call,
                     write a one-line summary to handoff.md."}] }'

The default is the policy

The worked comparison ran the same task four ways. What actually differs between them is one decision: does the side effect, the write to handoff.md, run on its own, or does it wait for you. Codex CLI waits by default (approval mode) until you pass --full-auto; the OpenClaw HTTP call writes without a pause. Below, you hold that switch. Flip APPROVAL_REQUIRED and rerun the write node to feel the difference the default makes.

The model produced the same line in both runs. The only thing that changed was whether the runtime applied it without asking. That switch is the default the CLI picks for you, and it is the whole of the agent's blast radius on a write.

Run the bare model your CLI wraps

Those CLIs are wrappers. The model doing the reasoning is just a chat-completion endpoint, the same build.nvidia.com model endpoint you used in Kickstart, authenticated with your nvapi- key. Send the same on-call task to a frontier model and read what comes back. A real CLI would add the working directory, the CLAUDE.md beacon, and the file-edit tools around this one call; here you talk to the bare model so the wrapper's job is easy to see.

Choosing among these tools is choosing a default policy, and defaults persist long after you stop paying attention to them. The defaults of the CLI wrapping the model are what set the agent's blast radius. Approval mode, a read-only sandbox, and an unrestricted shell session all use the same model and produce very different outcomes. Pick the wrapper whose defaults match the level of trust you actually want to extend.
