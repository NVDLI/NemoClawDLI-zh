The Index Agent

Data comes in several shapes, and each shape calls for a different retrieval strategy. Real-world corpora mix them, and matching the wrong strategy to the shape is the most common reason an Index Agent fails silently in production. The Index Agent brings outside knowledge to a Workflow Agent: a corpus indexed for retrieval, plus wiring that turns retrieval into an agent tool. This page covers the four data shapes, builds the fuzzy-prose case end to end (embed, index, retrieve, retrieve-as-tool), and points at where the other three shapes live in depth.

Naming the context bundle before you pick a store

Before picking a retrieval primitive, the Index Agent has to name its bundle: the complete, bounded set of context it needs in one package to do its job. For a single-turn QA system the bundle is small (one user question, one retrieved paragraph, one answer). For an autonomous agent the bundle is the working memory across many turns: constraints, prior decisions, partial results, tool surfaces, rules. Two things go wrong when the bundle is badly designed:

  • Rediscovery tax. The agent re-fetches the same piece of the bundle on every turn because the running state does not carry it forward. Cost scales linearly with turn count.
  • Stale bundle. The agent acts on a piece of the bundle that was true earlier but is no longer true. The decision is confidently wrong.

The bundle principle is a planning discipline: define the bundle before you pick the database. Picking a vector store first and hoping it covers everything is the origin of most "worked in demo but failed in production" stories. The four-shape taxonomy below is how you check whether your candidate primitive can deliver the bundle for your task.

Matching a retrieval primitive to the shape of your data

Each data shape maps to a different retrieval primitive. Mismatching the lane to the shape produces a silent retrieval miss, not a loud error. The four answers in the table below tell you which primitive to reach for.

Shape Examples Right primitive
Fuzzy proseDocs, articles, code comments, transcriptsDense vector + cross-encoder rerank
Hierarchical docsLegal contracts, technical manuals, nested specsTree index with parent pointers
Governed tablesCustomer records, financial ledgers, HR tablesSemantic layer (dbt / LookML) over the source of truth
Relational / graphOrg charts, code dependencies, knowledge graphsGraph traversal (Cypher, GraphQL, custom)

The rest of this module builds the retrieve-then-generate pattern, also called Retrieval-Augmented Generation (RAG), formalised by Lewis et al., Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks (NeurIPS 2020). The core idea is that, rather than relying solely on what the model learned during training, you retrieve relevant passages from an external corpus at inference time and inject them into the prompt. In theory, the model's answer is grounded in that specific evidence rather than in a possibly-stale memory. Concretely:

  • the query is embedded
  • the embedding runs through a retriever over a passage index,
  • the top-K passages are concatenated onto the prompt,
  • and the generator produces an answer grounded in those passages.

The embedding, the primitive everything else is built on

Every Index Agent in the fuzzy-prose lane starts from the same primitive. An embedding is a learned numerical address: text in, a fixed-length vector out, where semantically similar texts land near each other in vector space. Two practical consequences follow:

  1. You can compare texts cheaply: cosine similarity over the two vectors is one dot product plus two magnitudes.
  2. You can store texts by where they live in that space; a vector index is a data structure tuned for nearest-neighbour search.

Both follow from one primitive: the embedding model. This course routes embedding calls through helpers.embed, which proxies to build.nvidia.com via the course's hosted worker. No lab path, no local server required.

Embeddings API contract. The embeddings endpoint takes {input: string[], model: string, input_type: "query"|"passage"} and returns {data: [{embedding: number[]}]}. The NVIDIA embed models distinguish between query and passage embeddings: the same text gets a different vector depending on its role, because the training objective aligns query vectors toward their relevant passage vectors rather than toward identical texts. That asymmetry is what makes cosine similarity a reliable relevance signal. Embedding a query using the "passage" type (or the reverse) breaks the score function silently, producing lower recall with no error message.

A whole retriever in thirty lines of top-K cosine

A "vector database" is a fancy way to say what the Index Agent actually does: store passages alongside their embedding; given a query embedding, return the top-K closest passages by cosine similarity. Failure mode: stale embeddings. A vector index is a cache of an embedding model's outputs. Production systems have to defend against a few specific failures:
  • Swap the embedding model and every cached vector becomes meaningless until you re-embed every passage.
  • The provider silently upgrades the model; scores drift without any error.
  • Two services share an index but pin different model ids; the index returns nonsense to one of them.
Production systems pin the embedding model id alongside each cached vector and refuse to mix versions. The canonical pin for this course is nvidia/llama-nemotron-embed-1b-v2, served through the course's hosted proxy at build.nvidia.com.

Searching small chunks but returning the parent document

A plain top-K Index Agent has a recall-precision trade-off no embedding model solves. You must choose between short chunks and long documents:

  • Short chunks embed precisely (the vector represents a focused idea) but lack context (one sentence is rarely enough to answer with).
  • Long documents have context (every fact lands in its setting) but embed fuzzily (the vector is the average of many ideas).

The production fix is a hierarchy: index small chunks (precise retrieval), but on a hit, fetch the parent document (full context). Same primitives, two levels. The exercise below shows it with three parent docs split into short sentence-chunks and a query that returns the matching parent.

Wrapping the index as a tool the model decides to call

A retrieval index by itself is not an agent. The Index Agent is what you get when the index is wrapped as a tool the model can choose to call. The cell below does exactly that:

  1. A corpus is embedded once and held in an in-memory index.
  2. A retrieve(question, k) tool is declared with a JSON schema.
  3. The agent receives the user's question. It chooses whether to call the tool.
  4. If yes, cosine retrieval runs over the index; the top-K passages are appended as a tool message.
  5. A second LLM call writes the final answer grounded in the retrieved passages.

This is the canonical "retriever-as-tool" pattern. The same shape scales to production: swap the in-memory cosine function for a server-side FAISS+BM25+rerank pipeline, and only the executor changes. The tool schema, the agent loop, and the final answer step stay identical.

How the other three shapes are built

This lab builds the fuzzy-prose lane end to end. The other three are named here so you can recognise them in the wild and reach for the right primitive; each is a known production pattern, not a mystery.

  • Hierarchical docs. A chunker that preserves the heading hierarchy, plus atomic table extraction, parent pointers, and a dual index for structural and semantic search. You index the small child chunks for recall and fetch the enclosing parent on a hit, so the model sees the clause in its section, not stranded.
  • Page-image retrieval for figures and charts. A dual-vector setup that embeds the rendered page image alongside its text, so a query can pull a figure or a slide, not just the prose around it.
  • Governed tables. Not built in this course. The standard production pattern is a semantic layer (dbt, LookML, or a hand-rolled equivalent) sitting between the agent and the row-level data, exposing only the curated metrics the bundle requires.
  • Relational / graph data. The agent calls a graph-traversal tool (Cypher, GraphQL, or custom) instead of a vector store; the bundle it gets back is a sub-graph, not a chunk list, so explicit edges survive into the prompt.

Before you continue
