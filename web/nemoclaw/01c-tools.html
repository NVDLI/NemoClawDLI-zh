Tools at Scale

Tools let agents act and query their environments. Whether this includes databases, search, APIs, or even sub-agents, all we need to do is make sure the contracts for accessing them is solid and enforced. This contract is usually JSON Schema for predicting arguments, though it could be something like code generation (as we will see in later sections). This page wires the two-call cycle, shows multi-tool routing, calls a real web-search endpoint, hides a sub-agent behind a single tool, and ends with the MCP shape that is becoming the production standard for serving tools.

What a tool actually is

A tool is structured output plus an executor. The schema describes what the function takes, the model produces the arguments, your code runs the function, and the result lands as the next message. Multi-tool routing, MCP discovery, and agents-as-tools are all that same cycle with a different source of schemas.

The schema is the contract the model reads

When you give a model a tool, you publish a contract: a function's name, what it does, and what arguments it accepts. The model reads this and decides whether to call the function instead of answering directly. The cell below sends one question and one tool spec. Watch finish_reason to see whether the model chose to call or to answer directly.

Why schema-based calling is reliable. Before structured function calling, developers prompted models to emit tool calls in custom XML or hand-rolled JSON; those broke whenever the model paraphrased. Schema-based calling moves the contract into a first-class API field, and the LLM is forced to generate with server-side enforcement:
  • the schema is restructured into a format the model is specifically trained to work well with
  • the serving engine can illegalize token samplings that break contract grammar
  • the server's response bundles the LLM's predicted tool calls into a consistent tool_calls field.
Therefore, your dispatch code can largely rely on tc.function.name and tc.function.arguments being present and parseable.

Running the tool and feeding the result back to the model

In most cases, the model cannot execute your function directly. It can only request a call. You run the function, get the result, and append it to the message history as a "tool" role message. Only then does the model produce its final, user-facing answer. The cell below runs all three steps in sequence: request, execute, respond.

Wiring web_search to a live search API

The cell below wires web_search to Wikipedia's free, key-less search API, which runs entirely in the browser (CORS-open) and returns ranked articles with short extracts, enough for the agent to ground its reply without any server-side proxy or key. Part 4b swaps the executor to DuckDuckGo's Instant Answer API behind the same tool contract, so you can watch the contract stay fixed while the backend changes underneath it.

Name tools for what they do, not how they do it. A tool called duckduckgo_search is brittle: changing the backend forces you to update every prompt that references the name. A tool called web_search is durable. Its name describes a capability rather than an implementation, so you can swap the backend behind it (Wikipedia on this page, an Instant Answer API in the next section, a crawler or proprietary index later) and the schema, description, and every agent prompt stay untouched. The same principle applies to any tool that wraps an external service: name it for what callers ask for, not for the library or API that happens to fulfil the request.

Swapping the backend while the tool contract holds

Part 4 used the canvas-flow canvas. Here the same logic runs in a flat mountRunCell block so you can see it as one contiguous script. DuckDuckGo's Instant Answer API is free, key-less, and CORS-open, and it returns one curated answer (a definition, a computed result, an encyclopedia abstract) plus a few related topics, but only for a query it recognizes as a single named entity. Asking for nemotron returns the encyclopedia abstract, while asking for nvidia nemotron returns nothing, because that phrase is not one entity. Most real research queries land in the empty bucket, which is why this is a demo of a narrow entity lookup rather than a search you would ground an agent on. For ranked web results a production agent wires a real search API (Tavily, Brave, SerpAPI) or a self-hosted crawler.

That shape makes it the cleanest kind of black-box tool: query in, answer out, nothing to configure. helpers.instantAnswer returns the exact same { results, count, unreachable } shape as helpers.webSearch, so the tool contract from Part 4 does not change at all. Only the function name at the call site does. The agent still asks for web_search and reads the same numbered result block.

The tool contract stays fixed when the backend changes. Instant Answers is narrow and curated but runs anywhere with no setup. A richer crawler or a proprietary index can slot in behind the same web_search name when that depth is needed. The model never learns which backend served the answer.

Hiding a whole agent behind a single tool

Agents are tools. Hide complexity behind a sub-agent. A SQL agent over a database, a code agent over a Python environment, a knowledge agent over a repo: each one is easier to invoke as a single tool than to wire directly into the main loop.

The cell below exposes a sub-agent that knows a small customer table as one natural-language tool. The main agent never sees the rows; it only asks questions.

The cognitive-load lever. Every additional tool, schema field, and description sentence consumes context the main agent could use for its task. A sprawling flat tool list tends to perform worse than a small set of tools backed by sub-agents, because each loop only sees the tools relevant to its level.

Fetching tools from a separate server with MCP

MCP standardises tool serving: tools/list for discovery, tools/call for execution. Tools live in a separate process; the agent fetches them on connect. One agent client speaks one protocol to many servers.

Before you continue

  1. What happens when the model calls a tool with arguments that fail your validation? The current loop crashes; how would you make it graceful without giving the model false confidence that the call succeeded?
  2. The Part 5 sub-agent is opaque to the main agent. What information would you want it to surface back (in addition to the answer) so the main agent can decide whether to trust it on the next turn?
  3. The tool_choice parameter can be set to "required" or to a specific tool name. When would forcing a tool call be the right move, and what risk does it create?
