Tools at Scale

A tool extends an agent beyond text, letting it query databases, run searches, call APIs, and hand work to other agents. The model can lean on a tool dependably because every tool comes with a contract describing how it is called, most often a JSON Schema laid over its arguments, though later sections reach for generated code instead.

The real difficulty is one of number rather than of any single tool. One well-described tool is easy for the model to route to, but a flat list of dozens starts to crowd the context and nudges the model toward the wrong call, or toward no call at all.

Most of this page is about keeping that routing reliable as the list of tools grows.

  • It wires the two-call cycle, then shows multi-tool routing.
  • It calls a real web-search endpoint and hides a sub-agent behind a single tool.
  • It ends with the MCP shape that is becoming the production standard for serving tools.

What a tool actually is

Every tool combines a schema with an executor that runs behind it, and a single call moves through four hands in turn:

  • the schema describes what the function takes
  • the model produces the arguments
  • your code runs the function
  • the result lands as the next message

Multi-tool routing, MCP discovery, and agents-as-tools are all that same cycle with a different source of schemas.

The schema is the contract the model reads

When you give a model a tool, you publish a contract: a function's name, what it does, and what arguments it accepts. The model reads this and decides whether to call the function instead of answering directly. The cell below sends one question and one tool spec. Watch finish_reason to see whether the model chose to call or to answer directly.

Schema-based calling is reliable because the contract is enforced rather than requested. Before structured function calling, developers prompted models to emit tool calls in custom XML or hand-rolled JSON, and those broke whenever the model paraphrased its output.

The schema-based approach moves that contract into a first-class API field, and the model must now generate against server-side enforcement:

  • the schema is restructured into a format the model is specifically trained to work well with
  • the serving engine can illegalize token samplings that break contract grammar
  • the server's response bundles the LLM's predicted tool calls into a consistent tool_calls field.

Therefore, your dispatch code can largely rely on tc.function.name and tc.function.arguments being present and parseable.

Running the tool and feeding the result back to the model

In most cases the model cannot execute your function directly and can only request a call. You run the function and append its result to the message history as a "tool" role message, and only then does the model produce its final, user-facing answer.

Wiring glossary_search to a real tool

The cell below wires glossary_search to the in-page MCP server defined at the top of this page. That server is a catalog of NVIDIA terms with a ranked search over it that runs entirely in the browser with no key and no backend, returning short definitions with source links that are enough for the agent to ground its reply. The catalog is wired in by hand so the whole server stays readable in one place, and the course's shared web_search runs that same ranked query against the full NVIDIA glossary index shipped with the bundle. The glossary explorer opens that real index: every term, the live webSearch and instantAnswer source, and a box to run the exact query the agents call in the modules ahead.

Part 4b swaps the executor to an exact term lookup behind the same tool contract, so you can watch the contract stay fixed while the backend changes underneath it.

A tool name should describe a capability. A tool called nvidia_glossary_api is brittle: changing the backend forces you to update every prompt that references the name. A tool called glossary_search is durable. Its name describes what the caller wants done, leaving the API that fulfils the request free to change. Behind that name you can run the ranked search on this page, the exact lookup in the next section, or a richer index added later. The schema, the description, and every agent prompt stay untouched. Any tool that wraps an external service earns the same durability when you name it for the capability callers depend on.

Swapping the backend while the tool contract holds

Part 4 used the canvas-flow widget. Here the same logic runs in a flat mountRunCell block so you can read it as one contiguous script. The backend swaps from Part 4's ranked search to an exact glossary_lookup that returns the one entry matching a term's slug and returns nothing whenever the slug is absent from the catalog. Exact lookup is precise when the caller already knows the term and unforgiving when it does not, the opposite trade-off from ranked search. A real knowledge tool usually offers both, and when you need more depth, a richer source like a full docs index or the NVIDIA blog can slot in behind the same name.

That shape makes it a clean black-box tool that takes a term in and hands an entry back, and glossaryLookup returns the same { results, count, unreachable } shape as the ranked glossarySearch. The tool contract from Part 4 does not change while only the executor behind it does, so the agent still asks for glossary_search and reads the same numbered result block.

The model is the consumer the contract protects. Across this swap the agent kept asking for glossary_search and reading the same numbered block, with no hint that a different function produced it.

Design for that property, because when the model couples only to the contract you stay free to upgrade the backend whenever the task outgrows it.

Hiding a whole agent behind a single tool

A tool need not be a small function. An entire sub-agent can sit behind a single tool call. To the calling model it still looks like one tool, even though the agent on the other side may be answering questions about a SQL database, running code in a Python environment, or searching through a repository. Wrapping that capability as one tool is easier for the main loop to work with than wiring the whole sub-agent into it directly.

The cell below exposes a sub-agent that knows a small customer table as one natural-language tool. The main agent never sees the rows and can only ask questions.

The cognitive-load lever. Every additional tool, schema field, and description sentence consumes context the main agent could use for its task. A sprawling flat tool list tends to perform worse than a small set of tools backed by sub-agents, because each loop only sees the tools relevant to its level.

Fetching tools from a separate server with MCP

MCP gives tool serving a standard shape. The agent retrieves the list of tools a server offers with a tools/list call, then invokes any one of them with tools/call. Those tools live in a separate process that the agent connects to and queries when it starts up. Because the protocol is the same everywhere, the agent can connect to additional servers without learning a new interface for each one.

The cell below fakes a tiny MCP server in pure JavaScript with the same JSON-RPC shape MCP defines (no transport). The agent fetches the tool list, hands the schemas to the model, then dispatches tool_calls back through the server's tools/call handler. The agent loop is byte-for-byte identical to Part 2 while only the source of the tool list changes.

Before you continue

  1. What happens when the model calls a tool with arguments that fail your validation? The current loop crashes; how would you make it graceful without giving the model false confidence that the call succeeded?
  2. The Part 5 sub-agent is opaque to the main agent. What information would you want it to surface back (in addition to the answer) so the main agent can decide whether to trust it on the next turn?
  3. The tool_choice parameter can be set to "required" or to a specific tool name. When would forcing a tool call be the right move, and what risk does it create?
