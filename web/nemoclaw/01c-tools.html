Tools at Scale

In Module 1b you wired a single tool into the agent loop. That round-trip does not change here. The number of tools grows, though, and routing reliably gets harder with every one you add.

One well-described tool is easy for the model to route to. A flat list of dozens crowds the context and nudges the model toward the wrong call, or toward no call at all.

  • It scales the loop from one tool to many, where the model has to route.
  • It calls a real search endpoint and hides a sub-agent behind a single tool.
  • It ends with the MCP shape that is becoming the production standard for serving tools.

Every tool is the same round-trip

Whatever sits behind it, a tool runs the same four-step cycle you built in 1b, drawn below. Everything this page adds (multi-tool routing, real search backends, agents-as-tools, MCP) is that one cycle with a different source of schemas.

The server enforces the schema. Before structured function calling, you prompted the model to emit calls as custom XML or hand-rolled JSON, which broke the moment it paraphrased. Now the contract lives in a first-class API field. The serving engine constrains generation to the schema's grammar and delivers a consistent tool_calls field. Your dispatch code can then count on tc.function.name and tc.function.arguments being present and parseable.

Wiring glossary_search to a real tool

The cell below wires glossary_search to the in-page MCP server defined at the top of this page. That server is a catalog of NVIDIA terms with a ranked search over it that runs entirely in the browser with no key and no backend, returning short definitions with source links that are enough for the agent to ground its reply. The catalog is wired in by hand so the whole server stays readable in one place, and the course's shared web_search runs that same ranked query against the full NVIDIA glossary index shipped with the bundle. The glossary explorer opens that real index: every term, the live webSearch and instantAnswer source, and a box to run the exact query the agents call in the modules ahead.

The next section swaps the executor to an exact term lookup behind the same tool contract, so you can watch the contract stay fixed while the backend changes underneath it.

A tool name should describe a capability. A tool called nvidia_glossary_api is brittle: changing the backend forces you to update every prompt that references the name. A tool called glossary_search is durable. Its name describes what the caller wants done, leaving the API that fulfils the request free to change. Behind that name you can run the ranked search on this page, the exact lookup in the next section, or a richer index added later. The schema, the description, and every agent prompt stay untouched. Any tool that wraps an external service earns the same durability when you name it for the capability callers depend on.

Swapping the backend while the tool contract holds

The same loop runs here as a flat mountRunCell script, with one change: the executor. The earlier search returned a short blurb for each of several matches. This backend returns the whole article for the single best match, fetched from the term's cached glossary page. The schema and the loop do not move; only the source behind glossary_search got richer.

The model only sees the contract. It asks for glossary_search with a natural query and reads whatever comes back, unaware which backend answered. You can start with a blurb index and later swap in full articles or a live search without touching the loop. Accuracy may drift when a backend resolves a match differently, but the contract holds.

Hiding a whole agent behind a single tool

A tool need not be a small function. An entire sub-agent can sit behind a single tool call. To the calling model it still looks like one tool, even though the agent on the other side may be answering questions about a SQL database, running code in a Python environment, or searching through a repository. Wrapping that capability as one tool is easier for the main loop to work with than wiring the whole sub-agent into it directly.

The cell below exposes a sub-agent that knows a small customer table as one natural-language tool. The main agent never sees the rows and can only ask questions.

The cognitive-load lever. Every additional tool, schema field, and description sentence consumes context the main agent could use for its task. A sprawling flat tool list tends to perform worse than a small set of tools backed by sub-agents, because each loop only sees the tools relevant to its level.

Fetching tools from a separate server with MCP

MCP gives tool serving a standard shape. The agent retrieves the list of tools a server offers with a tools/list call, then invokes any one of them with tools/call. Those tools live in a separate process that the agent connects to and queries when it starts up. Because the protocol is the same everywhere, the agent can connect to additional servers without learning a new interface for each one.

The cell below fakes a tiny MCP server in pure JavaScript with the same JSON-RPC shape MCP defines (no transport). The agent fetches the tool list, hands the schemas to the model, then dispatches tool_calls back through the server's tools/call handler. The agent loop is byte-for-byte identical to a normal tool call while only the source of the tool list changes.

Before you continue

  1. What happens when the model calls a tool with arguments that fail your validation? The current loop crashes; how would you make it graceful without giving the model false confidence that the call succeeded?
  2. The agents-as-tools sub-agent is opaque to the main agent. What information would you want it to surface back (in addition to the answer) so the main agent can decide whether to trust it on the next turn?
  3. The tool_choice parameter can be set to "required" or to a specific tool name. When would forcing a tool call be the right move, and what risk does it create?
