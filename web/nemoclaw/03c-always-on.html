The Always-On Agent

The agent in 3b only ran when you sent it a chat completion. For most useful agents, the more interesting question is what they do without being asked. OpenClaw has a family of triggers for this: skills the agent picks up mid-turn, heartbeats it runs on a timer, cron jobs that fire in their own sessions on a schedule, and sub-agents a parent spawns to do focused work. They are the same machinery with different knob settings, which the table below lays out. The two you run on this page are the skill and the cron job.

Skills, heartbeats, cron, and sub-agents share one set of knobs

Every mechanism you will encounter here reduces to the same three knobs: session (whose context the run inherits), directive (the markdown file that tells the agent what to do), and trigger (what causes a run to start). Skills, heartbeats, cron, and sub-agents are all different combinations of these three, and none of them introduces new machinery.

The table is worth reading for what differs across rows rather than what repeats. Session scope, directive location, and trigger type are the only dimensions that vary, so any new mechanism you encounter is just a different value in one of those columns.

Step 1 · Add a Skill

A skill is nothing more than a markdown file placed under skills/. The agent picks it up on the next turn by reading its own workspace, with no restart, no redeployment, and no change to the system prompt is required.

# skills/triage-incident.md

When the user asks about a production incident, or pastes a log line
suggesting one, do these things in order:

1. Confirm the affected service and the time window.
2. Open the runbook for that service from /sandbox/runbooks/.
3. Suggest the smallest reversible mitigation; do not run it yourself.
4. Ask the user before opening a Jira ticket.

The widget below asks the agent to install that exact skill, then fires a chat completion designed to match it. The agent matches the request against each skill's description, so the prompt doesn't have to repeat the skill's name. Watch the agent invoke the new skill on the second turn.

Step 2 · Inspect your running agent

Scheduled jobs live on the gateway, not behind an HTTP REST route. The same WebSocket connection the Control UI uses exposes cron.list, cron.add, and cron.remove. A cron job is one way an always-on agent acts without a human in the loop: work that fires on a schedule, each run in its own fresh session, distinct from the heartbeat in the table above, which ticks the caller's own session on a timer.

The widget below connects, lists the crons already installed, and walks the full lifecycle of a new one. It installs a demo job that fires every minute and appends a line to MEMORY.md, waits for the first run, shows you the appended line, then removes the job so nothing lingers.

Cron jobs run unattended. A scheduled directive that asks the agent to "send the daily report" will fire whether you are watching or not. The fresh-session-per-fire knob is the safety mechanism: each run starts clean, so a bug in turn 1 can't poison turn 2. Module 4a adds a kernel-level containment layer on top of this: every filesystem access and network connection the cron-fired agent tries to make passes through an explicit allow-list before the syscall runs, so a misbehaving scheduled job can only reach what the policy permits.

Where to take this

Skills as memoised trajectories appear across the production ecosystem under different names and shapes:

  • Wang et al., Voyager (2023). The research origin, demonstrated in a Minecraft agent.
  • LangGraph Persistence. Checkpointed graphs as save-and-resume.
  • Anthropic, Agent Skills. The production skill-folder layout.

References

  • Wang et al., Voyager: An Open-Ended Embodied Agent (2023). The skill-library / memoised-trajectory mechanic this page builds on, demonstrated in a Minecraft agent.
  • Park et al., Generative Agents (2023). Multi-day autonomous-agent simulation; the reflection and memory-consolidation patterns an always-on loop reuses.
  • Anthropic, Agent Skills. The production skill-folder layout this page's skills/<name>.md drop-in mirrors.
  • LangGraph, Persistence (checkpointers). Checkpointed graphs as the same save-and-resume primitive in a different production shape.
  • cron(8). The canonical reference for the scheduling primitive the cron drop-in borrows.
