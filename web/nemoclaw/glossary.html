Where web_search actually looks

When an agent in this course calls the web_search tool you wire by hand in Module 1c, nothing leaves your browser. It ranks a glossary of NVIDIA AI and accelerated-computing terms that shipped with the page. That can sound like a shortcut, but it is the honest version of a tool: a fixed, inspectable corpus an agent can truly ground in, with no key, no network round-trip, and no surprise in what comes back. This page opens it up. Watch the index load, run the exact ranking the agent runs, and read the functions line for line.

One file, fetched once

The whole backend is a single static file, assets/glossary_index.json (… terms, …). It ships in the same bundle as the page, so the browser loads it same-origin with no key and no CORS. The first search fetches it; _shared.js then holds the parsed index in a module-level promise and every later search reuses it. The contents are regenerated from the live glossary by scripts/vendor_glossary.py, so the corpus is reproducible and auditable rather than a moving target.

Run the search the agent runs

This is the real pipeline behind one web_search call, one node per step. Edit the query in the first node and hit Run all: the index loads from cache, every term is scored, the top matches survive, and the result is formatted into the exact text block the model reads back. The scoring node holds the same algorithm helpers.webSearch uses, so change a weight and watch the ranking move.

The functions, in full

Two functions back the one tool contract, both returning { results: [{ title, body, href }], count, unreachable }. webSearch is the broad, ranked lookup the agent grounds answers in; instantAnswer is the narrow one that returns a single term's definition only when the query names it. This is their source, read live from _shared.js at load, so what you see here cannot drift from what actually runs.
