The materials catalog behind web_search

When an agent in this course calls the web_search tool you wire by hand in Module 1c, nothing leaves your browser. It ranks the course's materials catalog: a fixed, inspectable corpus that ships with the page. The catalog has two tiers, and the difference is the whole point of this page. Cached materials (the NVIDIA glossary) ship in full and the agent grounds in them offline. On-demand materials (papers, blog posts) ship as a searchable card plus a source link, pulled from the live web on a schedule rather than copied wholesale. Watch the catalog load, run the exact ranking the agent runs, see how it is kept current, and read the functions line for line.

Two tiers, one surface

The whole backend is one static file, assets/materials_index.json (… entries, …): … cached and … on-demand. It ships in the same bundle as the page, so the browser loads it same-origin with no key and no CORS. webSearch ranks both tiers together, so one query reaches a glossary definition and a paper abstract through the same surface.

Cached · the NVIDIA glossary

The 79-term glossary index ships in full, and seven terms also carry their complete vendored article. The agent can quote these directly, offline, with nothing to fetch. This is the material worth caching: small, stable, and read on almost every search.

On-demand · papers and posts

Larger sources (arXiv abstracts, the NVIDIA developer blog) ship as a catalog card (title, blurb, source URL) but not as full shipped text. The agent surfaces the card and follows the link for the rest. Less useful to cache, so it is reached through the same surface on demand.

How it stays current (and how you would fix it)

A vendored corpus drifts from its sources unless something keeps it honest. That job is one script, scripts/pull_materials.py, and it is built to make any problem obvious to everyone at once, in the same words.

So the loop is: a contributor (or the deploy build) runs the pull; every source is fingerprinted in _materials.json; --check re-fetches and flags drift or an outage; and the same status lands on the validation screen (reachable from the site's landing page, or reproduced locally with python3 scripts/validate_bundle.py) with the exact command to fix it. Nothing about the corpus is a moving target you have to trust.

Run the search the agent runs

This is the real pipeline behind one web_search call, one node per step. Edit the query in the first node and hit Run all: the catalog loads from cache, every entry (cached and on-demand) is scored, the top matches survive, and the result is formatted into the exact text block the model reads back, with each match's tier marked. The scoring node holds the same algorithm helpers.webSearch uses, so change a weight and watch the ranking move.

The functions, in full

Two functions back the one tool contract. webSearch is the broad, ranked lookup over the whole catalog the agent grounds answers in; instantAnswer is the narrow one that returns a single glossary definition only when the query names a term. This is their source, read live from _shared.js at load, so what you see here cannot drift from what runs.
