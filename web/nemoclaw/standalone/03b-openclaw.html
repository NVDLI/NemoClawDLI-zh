The OpenClaw Agent

OpenClaw is an agent runtime: a model wired to a tool palette, a server-side session that remembers across turns, and a workspace of markdown files that is its entire configuration. There is no Python orchestrator. The runtime reads that folder every turn, folds the files into the system prompt, hands the result to the model, and runs whatever the model asks for. The consequence worth dwelling on is that the configuration is just files, so the agent can read its own setup and you can reshape it by editing one file. This page is the introspection tour. You ask the agent to describe its own workspace, then change a single file and watch the next turn read differently.

The workspace, from the agent's point of view

Before every turn, the runtime reads the workspace folder, assembles its contents into the system prompt, and hands that prompt to the model. The folder is the configuration: change a file and the next turn reads differently.

.openclaw/workspace/ SOUL.md persona, boundaries, tone, values AGENTS.md operating instructions and rules IDENTITY.md name, creature, vibe, emoji USER.md who the human is, preferences TOOLS.md per-tool usage notes HEARTBEAT.md periodic autonomous-task checklist memory/ daily logs, one file per day 2026-06-11.md raw notes the agent appends as it works MEMORY.md curated long-term memory (loaded in the main session only) skills/ per-skill markdown bundles (next page)

Memory comes in two tiers, and the distinction is worth holding onto. The agent appends raw notes to a dated file under memory/ as it works, then distils what is worth keeping into MEMORY.md, its curated long-term store. The runtime loads MEMORY.md only in the main session, never in a shared or group context, so personal notes do not leak to strangers. You will read both straight off the live sandbox a few steps down.

Because the configuration is just files, the agent can describe its own setup accurately, so you can ask it directly and trust the answer. If you want to know what persona rules are active, what tools the agent knows about, or what it remembers about you, the answer is always in those files, and the agent can read and report them just like any other content in its context.

Step 1b · Read the workspace yourself

Step 1 asked the agent to describe its files. You do not have to take its word for it. Cloudflare puts an operator terminal in front of every launchable, and helpers.terminal() opens it straight from this page. Two entry points:

  • helpers.terminal("bash") opens the host VM shell, where you can run openshell sandbox list.
  • helpers.terminal("openshell sandbox connect <agent>") drops you inside the kernel-sandboxed agent, where the workspace lives.

The cell below connects into the sandbox and reads SOUL.md, the daily memory, and MEMORY.md off the running instance. Edit the command list and re-run to poke at anything.

The launchable has two planes of authority. The terminal runs as the operator, above the sandbox boundary, which is why it can read every file and list the sandboxes. The agent inside runs under the OpenShell policy you meet in Module 4. The two share one machine but hold different authority.

Step 2 · Two scenarios, side by side

Because the persona is just a file, swapping SOUL.md is all it takes to produce a fundamentally different agent voice. The widget under each scenario sends a tagged session that the gateway routes to a different SOUL.md, so you can see the same question answered by two different configurations without touching any code.

Scenario A · Default SOUL.md

Stock OpenClaw: friendly, terse, and willing to use any tool the policy permits, which makes it a good fit for development.

Asking it to summarise a doc gets you a tight summary plus a note about what tools it would reach for next.

Scenario B · "Auditor" SOUL.md

A persona slotted in for code review: it refuses to run code until it has named the risk surface, and it cites the file it is reviewing on every claim.

Asking it to summarise the same doc gets you a risk list plus pointed questions about what's not in the doc.

You did not edit SOUL.md. The cell above just tagged each turn with a different session key. Your launchable keeps a stash of pre-built SOUL variants, and the suffix routing that maps a session key to one of them is a lab affordance wired into the NemoClaw image. Outside the lab the gateway has no such stash, so the same two session keys would read the one SOUL.md you have and return two identical replies. In production you get the swap by editing the file itself: the file-as-context mechanic IS the persona change, so you write a new SOUL.md (or skill bundle) and the next turn reads it.

Step 3 · The agent edits its own context

Ask the agent to write a preference to MEMORY.md, then ask it back on the next turn. The model itself has no persistent state, so the second turn can only answer because the runtime carried the preference forward: the session history it holds, plus the MEMORY.md the agent saved. The runtime is doing the remembering, not the weights. (MEMORY.md is what would let it survive a brand-new session, where there is no history to fall back on.)

Why this matters for safety. If the agent can write its own context, the containment layer is what stops a bad write from doing harm. The split is doing real work: OpenClaw can freely modify markdown in its own workspace; the OpenShell sandbox beneath it is what prevents the same write call from touching the host filesystem, the network, or another agent's workspace. You will see this boundary tested directly in the next module, where a deliberately over-privileged agent tries to cross it.
