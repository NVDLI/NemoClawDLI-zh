工具的规模化应用

在模块 1b 中，您将一个工具接入了智能体循环：模型请求调用一个具名函数，执行框架运行该函数，再将结果传回下一次模型调用。此处的往返过程并未改变，变化的是工具界面：模型必须从更多描述中作出选择，而每个工具背后都可能隐藏着更强大的能力。

本页将沿着这一契约，依次介绍本地函数、搜索后端、子智能体，最后介绍 Model Context Protocol (MCP) 服务器。这些方式都能为同一个循环提供能力。冗长而扁平的工具列表还会占用上下文，并可能降低路由可靠性，因此模块 2 将采用限定范围的工作流。

工具调用约定保持不变

下图呈现了模块 1b 中的循环。后续各节会改变模式的来源和执行器的行为，但模型仍会请求调用具名工具并读取其结果。

服务器负责执行模式约束。在结构化函数调用出现之前，应用通常需要从模型文本中解析自定义 XML 或手写的 JSON。模型只要换一种表述，就可能导致解析器失效。tools 字段将约定单独传递，因此推理服务引擎可以约束参数，使其符合模式，并返回格式一致的 tool_calls 字段。这样，分派代码便可以确信 tc.function.name 和 tc.function.arguments 始终存在且可解析。

模型如何在多个工具之间作出选择

智能体很少只有一个工具。当存在多个工具时，模型会根据 description 字段决定调用哪一个。

下方单元为模型提供两个工具和一个需要从中作出选择的问题，可视化结果会显示模型选择了哪个工具以及选择原因。

将 glossary_search 接入真实工具

该单元将 glossary_search 接入页面内的 NVIDIA 术语目录。排序搜索无需密钥即可在浏览器中运行，并返回带来源链接的简短定义。课程共享的 web_search 会对完整目录应用相同的排序方式。打开术语表浏览器即可查看所有术语、阅读实时的 webSearch 和 instantAnswer 源代码，或自行运行查询。

下一节会将执行器替换为位于相同工具约定背后的精确术语查询，让您直观看到：底层后端虽已改变，工具约定仍保持不变。

工具名称应描述一种能力。名为 nvidia_glossary_api 的工具很脆弱：一旦更换后端，您就必须更新所有引用该名称的提示词。名为 glossary_search 的工具描述的是调用方所需的能力。排序搜索、精确查询或更丰富的索引都可以置于该约定之后，无需更改智能体提示词。

更换后端，同时保持工具约定不变

此处以扁平的 mountRunCell 脚本运行相同循环，只有一处变化：执行器。之前的搜索会为多个匹配项分别返回一段简短说明。此后端则会从该术语的缓存术语表页面中，获取最佳匹配项的完整文章。模式和循环均未改变；只是 glossary_search 背后的数据源变得更加丰富。

模型只能看到约定。它使用自然语言查询请求 glossary_search，并读取返回的内容，却不知道是哪个后端作出的响应。可以先使用简短说明索引，之后再替换为完整文章或实时搜索，无需修改循环。如果不同后端采用不同方式确定匹配项，准确性可能会发生变化，但约定仍然有效。

将整个智能体隐藏在单个工具之后

工具不一定是小型函数。整个子智能体也可以封装在一次工具调用之后。对于调用模型，子智能体仍表现为一项约定。在该约定背后，它可以查询数据库、运行代码或搜索代码库，无需向主循环暴露这些内部工具。

下方单元将一个熟悉小型客户表的子智能体作为单个自然语言工具开放。调用方始终看不到表中的数据行，只能提出问题。

调节认知负荷的杠杆。每增加一个工具、一个模式字段或一句描述，都会占用主智能体原本可用于执行任务的上下文。庞大而扁平的工具列表往往不如由子智能体支撑的精简工具集，因为每个循环只需看到与自身层级相关的工具。

使用 MCP 从独立服务器获取工具

Model Context Protocol (MCP) 为工具服务提供了标准形式。智能体通过 tools/list 获取服务器的工具目录，并通过 tools/call 调用所选条目。这些工具运行在独立进程中，智能体启动时会连接该进程并进行查询。由于各处采用相同协议，智能体无需为每台服务器学习新的接口，即可连接更多服务器。当工具发现和传输需要共享协议时，请使用 MCP。如果执行框架已经知道能力的位置和调用方式，则使用本地函数、仓库技能或直接的 API 调用。

发现过程也是信任边界。请将 tools/list 响应视为不可信输入。连接服务器之前：
  • 验证其身份，
  • 向用户显示所请求的能力，
  • 授予满足使用需求的最小权限范围，
  • 并将每项凭据绑定到该服务器对应的受众。
对于远程连接和 OAuth 发现，请拒绝私有地址和链路本地地址，并验证每一次重定向。 MCP 安全指南要求客户端负责用户同意、token 处理以及服务器端请求伪造（SSRF）控制。

下方单元使用纯 JavaScript 模拟了一个微型 MCP 服务器，其形式与 MCP 定义的 JSON-RPC 相同（不含传输层）。智能体先获取工具列表，将模式交给模型，然后通过服务器的 tool_calls 处理程序分派 tools/call。智能体循环与普通工具调用逐字节完全相同，改变的只有工具列表的来源。

模块 2 会保留此工具约定，并改变外层结构。工作流可以按固定流程分派调用、将任务分流到多个分支，或把一项专门任务委派给另一个循环，无需向调用方暴露所有内部工具。

继续学习之前

  1. 如果模型调用工具时传入的参数未通过验证，会发生什么？当前循环会崩溃；您会如何让它妥善处理这一情况，同时避免让模型误以为调用已经成功？
  2. 作为工具使用的子智能体对主智能体并不透明。除了答案之外，您还希望它返回哪些信息，以便主智能体在下一轮判断是否可以信任它？
  3. tool_choice 参数可设置为 "required" 或特定工具名称。在哪些情况下应该强制执行工具调用？这样做会带来什么风险？
  4. 在向此智能体添加远程 MCP 服务器之前，您会验证哪些身份、能力范围、token 受众和网络目标？如果未经验证就接受，其中哪一项会成为 SSRF 路径？

参考资料

  • Schick et al., Toolformer: Language Models Can Teach Themselves to Use Tools (2023)。这篇论文奠定了自监督工具使用的基础；此后所有函数调用规范都可视为它的变体。
  • OpenAI 函数调用指南。 tools=[…] 载荷遵循此规范；托管版本的 API 入口会将这种格式代理到任意提供商。
  • Model Context Protocol (MCP) 规范。本模块 MCP 部分介绍的跨供应商工具发现和工具服务层（由 Anthropic 发起，现已成为开放项目）；它在智能体运行时层面与函数调用形成互补。
  • MCP 安全最佳实践。MCP 客户端和运维人员需要关注的用户同意、限定受众的凭据、SSRF 控制措施和本地服务器执行风险。
  • Anthropic 工具使用参考。这是 Claude 的对应实现，适合用于跨供应商比较。
