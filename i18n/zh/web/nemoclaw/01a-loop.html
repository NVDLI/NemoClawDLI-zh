智能体

智能体是指能够在任何有意义的层面上与环境交互的实体。从这个意义上说，处理日常事务的人是智能体，将房间维持在设定温度的恒温器，以及在车流中行驶的自动驾驶汽车，同样也是智能体。

它们都会通过传感器感知环境，并通过执行器对环境采取行动。每次行动都会产生下一次观察，因此感知和行动会连成一个持续运转的周期，即感知—推理—行动循环。只要智能体仍在交互，这个循环就会持续。您将构建的所有智能体都采用同一循环，区别仅在于它们能感知多少信息，以及行动能够影响多大范围。

循环的三个环节

循环每运行一轮都会经过三个环节，每个环节都有直观的名称和明确的职责。

  • 感知为智能体提供它对环境的全部认知。恒温器只读取一个数值：当前温度。自动驾驶汽车则融合摄像头、雷达和地图信息，构建道路模型。感知所捕获的信息就是智能体能够利用的全部信息，因为后续环节都不会直接接触现实世界。感知中的盲区会成为智能体其它部分无法弥补的盲区。
  • 推理将感知结果转化为决策，不同智能体的推理方式可能大不相同。恒温器只需将当前温度与目标温度进行比较，而国际象棋引擎会搜索数百万种走法，自动驾驶汽车则会运行学习得到的策略。您将在此构建的智能体通过调用语言模型进行推理，而本课程后续添加的几乎所有能力（工具、记忆和规划）都依托于这一步。
  • 行动会改变智能体自身及其它参与者所处的环境。行动可以简单到切换继电器，也可以复杂到操控汽车。后续页面会将暴露给模型的代码称为工具，因为从模型的角度看，它只是另一种可用的行动。调用工具，就是将执行这段暴露的代码作为行动。行动空间也界定了智能体能力所及的最外边界，因为无论推理能力多强，智能体都只能通过行动空间影响现实世界。
推理步骤可以替换。感知和行动并不关心二者之间采用的是哪一种决策函数。简单规则、决策树、搜索程序或神经网络都可以驱动同一个循环。只需构建一次固定的循环框架，就能清楚区分两个问题：推理能力有多强，以及行动能够影响多大范围。

经典智能体设计的区别在于决策步骤。Russell 和 Norvig 的 Artificial Intelligence: A Modern Approach 将这些设计排列成一条谱系：从仅具备反射机制的智能体，到能够改进自身规则的学习型智能体。本课程先从固定逻辑入手，再加入语言模型和经过设计的上下文，逐步构建基于模型、以目标为导向的循环。后续模块会让这一循环在不断变化的状态下持续运行，这正是学习型智能体赖以发展的模式。

不使用语言模型的智能体

推理调用 LLM 后会发生什么变化

可以像调用其它函数一样调用聊天补全接口：向它传入消息列表和模型名称，它会返回一条助手消息及元数据。

关于 chat()。这是课程提供的封装函数，您稍后将在本页下方实时运行它。下面的代码片段会预先展示其调用形式和返回字段，让您在进入运行时单元格时已熟悉这些名称。 
const reply = await chat({
  model:    "nvidia/nemotron-3-nano-30b-a3b",
  messages: [{ role: "user", content: "Hi" }],
});
// reply.choices[0].message  → { content, reasoning_content }
// reply.choices[0].finish_reason → "stop" | "tool_calls" | "length"

该函数的三个特征决定了基于它构建的智能体必须如何运行：

  • 各次调用不共享状态。两次请求之间，服务器不会替您保留任何内容。如果希望模型记住上一轮对话，您需要再次发送该轮内容。对话的“记忆”就是由代码维护，并在每次调用时重新发送的消息列表。
  • 输出包含两个通道。推理模型会将推理过程记录在 reasoning_content 中，并将最终答案放在 content 中。开发期间，可以检查这些推理记录；循环的下一阶段则读取 content 中的答案并据此行动。
  • finish_reason 是循环的退出条件。 "stop" 表示模型已生成最终答案。"tool_calls" 表示模型希望代码运行指定函数，并将结果返回给它。 "length" 表示模型尚未完成时，token 预算已耗尽。驱动基于 LLM 的智能体时，整个循环都围绕读取这一个字段并决定下一步操作来构建。

本课程始终使用 Chat Completions API：您需要在自己的代码中以 messages[] 数组保存对话，并在每一轮重新发送完整数组。较新的 Responses API 则可以在服务器端保存对话线程，因此您只需发送新输入以及对上一轮的引用。无论采用哪种方式，模型在各次调用之间都保持无状态且不会发生改变。对话存在于模型之外，由代码或服务器维护相应状态。

chat() 实际发送的内容

chat() 是一个便捷封装函数，封装了采用 OpenAI 兼容传输格式的普通 HTTP POST。该请求包含三项内容：

  • 请求发送到的入口；
  • 一个携带密钥的 Authorization 标头；
  • 以及包含 model 和 messages 的 JSON 正文。

下面的单元格会手动发起该调用，并展示请求和响应两端的内容。打开 request，查看隐藏密钥后从浏览器发出的内容；打开 原始响应，查看 chat() 返回的完整对象。

本课程中的每个入口都采用相同的格式，包括模块 3 中的 OpenClaw 智能体运行时。

这次调用还在悄然完成两件事，以及这样做的原因。这两件事都不神秘，在您信任它们之前，都值得先了解清楚。
  • 请求可能会经过代理。如果您在输入 API key 时选择了学习管理系统/iframe 设置，请求就不会直接发往 build.nvidia.com。该入口不会返回跨源 (CORS) 标头，而浏览器 fetch 要求必须提供这些标头，因此调用会经由一个小型直通代理转发，由代理添加这些标头。代理还会添加课程归属标头，以便 DLI 识别来自本资源的流量。课程会随该请求发送 API key，但不会存储它，也不会替换为其它密钥。
  • 流式处理封装在辅助函数中。 chatStream() 会发送同一个聊天请求并启用流式传输，然后将返回的事件流解析为回答文本、推理文本、用量元数据和最终完成信号。该辅助函数还会把这些内容连接到课程面板和 Stop 按钮，使单元格可以专注于概念，无需处理流式传输的底层细节。可以从单元格菜单中打开辅助函数源代码，查看它具体执行了哪些操作。

保持循环不变，替换推理步骤

您现在已经具备智能体的两个组成部分；上面的无状态 chat() 函数可以很好地与前一个反射式智能体的感知—推理—行动循环结合。在将模型接入这个循环之前，不妨先观察决策步骤如何使用并非语言模型的例程。

按顺序运行各节点。每个节点都会将不同的决策规则放入同一个迷宫求解循环：

  • 固定的“始终向东”规则可以在笔直走廊中抵达终点，但会在迷宫的第一堵墙前停滞，因为固定朝向无法转弯。
  • DFS 会深入探索，并从死路回溯。
  • BFS 会逐层向外扩展，然后沿最短路径前进。
  • A* 会让同样的逐层扩展偏向终点。
只有决策步骤会发生变化。 DFS、BFS 和 A* 都会读取当前迷宫状态并返回一个移动动作。最后一个节点中的一行代码用于选择决策函数；无论选择哪一个，下面的循环都会以相同方式运行。您刚刚运行的 chat() 调用也可以承担同一个步骤。它改变了两处衔接：代码将感知结果呈现为文本，模型则返回由代码执行的工具调用。下一节将具体讲解这两处衔接。

使用语言模型选择迷宫移动动作

迷宫循环仍会对环境进行采样，并执行一个经过验证的移动动作。只有决策步骤发生变化。模型不再使用 DFS、BFS 或 A*，而是读取呈现出的迷宫，并请求代码调用 choose_direction。

按以下顺序运行单元格，然后每次只调整一个控制项：

  1. 先运行引擎节点。它会导出迷宫实用工具和一个共享控制器 state.runMaze；该控制器会自动穿过走廊，仅在岔路口调用模型。
  2. 运行下面可编辑的迷宫智能体节点。DIRECTIVE 是核心系统指令，选项对象则控制模型、迷宫大小、文本地图、图像附件、移动历史、坐标轨迹以及重复提供的工具模式。
  3. 先使用可正常工作的默认设置。然后开启 includeImage 测试渲染后的迷宫，切换 model 比较不同模型，或者在简单情形运行成功后设置 advanced，扩大迷宫。
模式将回答转换为类型化动作。固定规则返回一个字符串，BFS 返回一个列表。choose_direction 为模型提供相同的契约，但通过 JSON Schema 强制执行该契约，使循环读取类型化值，而不是解析自由文本。有了它，语言模型便可接管刚才由 BFS 和 A* 承担的决策步骤。

在本地绘制循环

将 chat() 调用放入会重新发送历史记录的循环后，本课程中任意 LLM 智能体的单轮运行都会呈现相同的四阶段结构。现在请记住这些阶段的名称，因为后续的每个安全性和可靠性问题都可以追溯到这四个箭头之一。

  • 局部采样。代码读取环境的一个局部切片，例如迷宫中的当前单元格及其有效移动方向、最新的用户消息，或某个文件的内容。它不会试图一次获取整个世界，因为当前这一轮只需要模型此次行动所需的那一小部分状态。
  • 局部感知。该切片会被呈现为完整的工程化上下文：系统提示词、持续累积的 messages[] 历史记录、先前的工具结果，以及您刚刚采样的切片。所有内容都是纯文本。对于 LLM 智能体，感知就是上下文工程。
  • 局部行动。模型将这些文本映射为更多文本：一个意图信号。理想情况下，它是类似 { "move": "east" } 的类型化工具调用，而不是自由文本。该意图只是在请求执行动作，本身从不执行任何操作。代码会读取它，在验证后对环境应用一次范围受限的更新 (doMove(...))。
  • 局部影响。更新会改变环境。模型内部不会持久保留任何内容。唯一持久的状态是环境，以及代码将重新构建的上下文。下一轮的局部采样会读取已改变的环境，随后循环再次开始。

请仔细观察该列表的中间部分。从感知到行动的步骤是一次无状态的文本到文本映射：输入完整的工程化上下文，返回一个意图信号。模型只负责转换文本，因此在这次映射的两端，感知环境以及将意图转化为实际变化仍然是代码需要完成的工作。

因此，下面的绿色框是唯一并非由您编写的部分。智能体实际上只有两个选择：您向其上下文中提供什么，以及您如何处理它返回的意图。

循环的每一轮都只在局部行动。模型读取环境中的一小部分，例如一个迷宫单元格，然后返回一个范围受限的动作；两者之间的无状态文本到文本步骤随即忘记刚才看到的一切。一个能够完成大量工作的智能体，本质上只是多次重复这个简单循环，同时由环境将状态从一轮传递到下一轮。模块 1b 将用代码构建这个循环，让您看到上下文如何随每轮运行而增长。

继续学习之前

只需编辑上方 LLM 迷宫单元格中的一个设置并重新运行，即可回答每个问题。

  1. 不向多模态模型提供文本。设置 includeText:false 和 includeImage:true，然后重新运行。此时模型只能看到渲染后的迷宫图像。它仍能抵达终点吗？与同时使用文本和图像的运行相比，它是否需要作出更多次决策？
  2. 从 DIRECTIVE 中移除策略提示。删除要求优先选择未访问分支而非已访问单元格的那一行，然后重新运行同一单元格。将决策次数与保留该提示时的运行结果进行比较。模型的能力有多少来自这一句话？
  3. 更换决策模型。将 model:"vision" 改为 model:"super"，然后重新运行。循环、迷宫、感知和行动均保持不变，只有负责选择移动动作的模型发生变化。更大的文本模型能否用更少的决策抵达终点？
