工作流智能体

单个 ReAct 循环可以处理大多数一次性任务，但更困难的问题有时需要一种结构，在下一个工具结果返回之前就决定要执行的工作。工作流智能体是指由执行框架控制工作流的智能体系统：该工作流由模型调用、确定性代码步骤、工具调用和专家循环组成。以下情形适合采用这种结构：并行运行的子任务可以共享结果；可以在工具运行前制定计划；或者路由应遵循规则，而不是取决于最近一次观察结果。

执行框架可以围绕一次模型调用、一个确定性步骤、一个专家循环或一组并行分支界定工作流范围。在每个边界处，执行框架都会决定哪些上下文可以跨越边界、哪些部分可以分支，以及哪些结果将传入工作流的下一阶段。扇出和固定路由让这种控制清晰可见，同时保留上一页介绍的 ReAct 循环。

两种关键模式的区别在于模型何时做出决定

响应式 · STEP-BY-STEP

ReAct（推理 + 行动）

在每一步中，模型都会先读取最新观察结果，再选择行动并运行工具；随后评估返回结果，再次作出选择。智能体会对上一次工具调用的返回结果作出响应，因此工具使用路径是在运行过程中逐步形成的。当执行路径取决于中间结果时，ReAct 表现出色；而当多个步骤本可同时运行时，它的表现则较弱。

论文：Yao et al., 2022。

审慎规划式 · PLAN-THEN-执行

ReWOO（无观察推理）

在任何工具开始运行之前，模型会通过一次 LLM 调用预先写出完整计划。随后，确定性执行器通常会并行运行计划中指定的所有工具，再由第二次 LLM 调用读取返回结果并进行综合。由于计划始终看不到工具结果，模型是在“无观察的情况下推理”。因此，当各步骤彼此独立时，ReWOO 表现出色；而当后续步骤需要根据前序结果作出响应时，它的表现则较弱。

论文：Xu et al., 2023。

在实践中，可以同时采用两者。许多实际系统会同时借鉴这两种方法。ReAct 循环所调用的工具可能会在内部运行预先规划的 ReWOO 式工作流；而通过 planner 预先安排工作的系统仍需要子智能体执行各个步骤，这些子智能体本身通常也是 ReAct 循环。请根据各自优势组合这些软件组件，并将工作流智能体用于可拆分为独立工作流的任务。

单一循环何时优于拆分成多个智能体

如果没有独立工作流，组合多个智能体所产生的协调开销便不会带来任何收益，而一个普通循环反而更快、更易调试。

开销具体体现在哪里。每个智能体边界都会增加模型调用延迟和路由逻辑，还会引入一个新的消息格式错误来源，并将清晰易读的时间线变成一条向多个工作单元分叉的执行轨迹。

无论任务是什么，这项开销都是固定的，因此关键在于工作收益能否覆盖它。对于一个提示词就能处理的线性任务，额外调用及其所需的路由逻辑永远无法收回成本。只有当任务本身具备某种结构，而单一循环只能被迫将其压缩为一条时间线时，拆分才开始体现价值。只要满足以下任一条件，这项权衡就值得。

  • 专业分工很重要。不同工作流需要不同的系统提示词、工具或模型。强迫一个智能体同时承担两种角色，会使两方面的表现都下降。
  • 可以并行处理。两个工作单元可以并发运行，而单个智能体只能依次执行。三项独立搜索可在其中最慢一项所需的时间内全部完成。
  • 上下文膨胀确实存在。由单个智能体包办所有工作会累积 10000-token 上下文，而各个专用智能体可以专注于各自负责的部分。
  • 故障隔离很有帮助。某个工作单元崩溃不会导致整个任务失败。编排器可以重试、跳过它或选择其它路由。

针对 NVIDIA 术语表运行 ReWOO 工作流

以下单元针对 NVIDIA 术语表运行 ReWOO 工作流，并对计划要求的每次检索使用 helpers.webSearch（您在模块 1c 中接触过的术语表排序搜索）。术语表浏览器会显示此搜索所用的完整索引，还可让您运行 planner 可能生成的任何查询：

Promise.all 是 JavaScript 中用于启动多个 promise 并等待它们全部完成的辅助函数。在这里，它只负责实现并发：既不调用模型，也不决定要运行哪些搜索。

  1. Planner。一次受 schema 约束的 LLM 调用会生成包含 3 至 5 个搜索查询的 JSON 列表。
  2. 执行器。使用纯 JavaScript。每个查询都通过 Promise.all 并发运行，此阶段不进行 LLM 调用。
  3. 综合器。第二次 LLM 调用读取所有结果并撰写简报，同时按索引引用每项搜索。

总共进行两次 LLM 调用，外加 N 次并行术语表搜索。编辑研究目标，观察 planner 的查询列表如何变化。

使用固定枚举将工单路由给一个专用智能体

路由是多智能体的另一种组织方式：分流智能体对输入进行分类，再将其交给一个专用智能体。由于分类器必须输出固定枚举中的一个类别，因此输出需要遵循严格的约定。固定枚举是一个封闭的允许标签列表；如果模型返回其它任何值，路由都应拒绝该结果或在更严格的指令下重试，而不能自行猜测。下游每个专用智能体都有范围明确的系统提示词，无需查看分流智能体的推理过程。

将一个共享输入同时分发给多个专用智能体

ReWOO 工作流在设计上就是并行的，因为它规划的每个查询都会针对术语表并发运行。另一种更常见的并行模式是将一个共享输入分发给多个专用智能体；每个智能体都有自己的系统提示词，并且全部同时运行。在执行轨迹中，总耗时取决于最慢的专用智能体，其它智能体则在这段时间内重叠运行。甘特图会显示每个专用智能体的运行时长，并且所有智能体共享一项网络搜索结果，从而将成本控制在一定范围内。

通过工厂声明专用智能体，无需逐个手动编写

上述四项练习都使用相同的几段样板代码手动构建了一个小型智能体，而生产代码不应在每次新增专用智能体时都重复编写这些内容。它们包括角色标签、系统提示词、工具列表和调用方式。工厂模式将这四个可变部分参数化，使您只需声明专用智能体，无需逐个编写：

  • 角色。用于日志记录和路由的简短标签。
  • 系统提示词。行为约定：它要做什么、拒绝做什么，以及如何组织回复。
  • 工具。它可以调用的函数（如有），这些函数使用 JSON-Schema 描述。
  • 调用约定。采用统一形式（specialist.run(input)）并返回最终回复。

CrewAI、 LangChain 和 LangGraph 都以各框架特有的名称提供了同一种工厂，无论其名称是 Agent、create_agent，还是角色/目标 dataclass。以下单元使用相同的四个参数构建两个专用智能体：一个算术辅导智能体和一个翻译智能体。两者处理同一个输入，回复并排呈现。

参考资料

  • Xu et al., ReWOO: Decoupling Reasoning from Observations (2023)。本模块的工作流智能体采用了 planner / worker / solver 分解方式。
  • Wang et al., Plan-and-Solve Prompting (2023)。这是更简单的前身：一次 LLM 调用写出计划，同一个 LLM 逐步执行计划。ReWOO 将 planner 与执行器分离。
  • Madaan et al., Self-Refine: Iterative Refinement with Self-Feedback (2023)。迭代式多轮研究背后的模式：智能体评判自己的输出并重新运行，直到达到质量阈值。
  • LangGraph。这是一个生产级框架，将本模块手动勾勒的工作流/状态机模式正式化。

动手尝试 · 实时分流路由

提出一个支持问题后，该交互组件会先通过一次模型调用将其归入一个类别，再将该工单路由到匹配的专用智能体系统提示词，并以该智能体的口吻流式返回答案。它运行的正是上面所示的“先分类、后交给专用智能体”模式。这里使用客户支持类别，而非 IT 服务台枚举。四个值分别是 billing、technical、账号和其它。更换领域时，只有类别列表会变化，底层路由机制保持不变。
