索引智能体

数据有多种形态，每种形态都需要不同的检索策略；为数据匹配了错误的策略，是索引智能体在生产环境中悄然失效的最常见原因。

索引智能体通过开发者定义的工作流，将这一工作流理念应用于外部知识。它会预先对语料库进行嵌入和索引，然后检索匹配的段落，并依据范围受限的上下文包生成答案。接下来的构建先沿这一路径处理非结构化文本，再将检索封装为工具，供外层 ReAct 循环调用。对于其它数据形态，课程将提供深入学习的相关指引。

RAG 的起源：一个经过端到端训练的系统

如今普遍使用的 RAG 已舍弃原始设计中的大部分机制。了解这一点，会改变您对即将接入的检索器的认识。

2020 年， Lewis 及其同事提出检索增强生成 (RAG) 时，它并不是一个外接搜索框的模型。检索器和生成器会针对需要执行的任务共同训练。请先从左向右阅读图示，再查看顶部横贯全图的箭头。

该设计的关键在标有 "End-to-End Backprop through q and pθ" 的箭头中。一个损失函数会同时更新两部分。查询编码器学习生成器可以利用哪些段落，生成器则学习更多依赖检索到的证据，而非自身记忆。

检索器最初就是模型的一部分，并由需要执行的任务塑造。直到很久以后，人们才将其描述为置于模型之前的搜索工具。

为什么如今的 RAG 不再采用联合训练

如今几乎没有人再以这种方式训练 RAG，主要有两个实际原因。您无法对通过 API 访问的前沿模型执行反向传播；即使自行托管，端到端检索训练也成本高昂且很容易变得不稳定。

实践最终采用了一种更简单的组合方式：取一个已有模型，将其冻结，再在前面接入检索器，让提示词在送达时已经载入证据，完全不进行训练。各个组件分别构建后再拼接起来。久而久之，"RAG" 开始指代这种外接式方案，而不再是论文所述的联合优化系统。

外接式方案的代价。如果检索器从未接触生成器的损失函数，就只能猜测生成器需要什么，因此检索质量的上限取决于嵌入模型与数据的匹配程度。重排序、查询改写和经过微调的嵌入模型，都只能补回端到端训练原本自然获得的一小部分能力。完善的检索栈需要不断增加处理阶段，才能找回其余能力。将外接式方案理解为对曾经统一系统的一种务实替代，您就能看清它的能力上限，以及哪些调节手段可以提高这一上限。

您将构建的“先检索、后生成”工作流

了解这一上限后，下面来看完整的组合架构。检索器位于冻结模型之前，系统沿两条独立的时间线运行：一条时间线提前构建索引，另一条则利用该索引处理实时请求。下图展示了这两条时间线。

离线：对每个段落生成嵌入并存储，以便快速查询，一次性构建索引。

实时：对问题生成嵌入，检索 top-K 个段落，再将这些段落与问题一同传给模型。

本页接下来的内容将逐阶段构建实时路径。

选择存储方案前，先定义上下文包

选择检索原语之前，您应先定义一个上下文包。上下文包是您打算在工作流中传递的一组完整且边界明确的上下文。

  • 对于简单的单轮问答系统，上下文包可以很小：用户问题、为回答该问题而检索到的少量文本块，以及答案本身。
  • 对于自主智能体，上下文包是它在多个轮次间携带的工作记忆。其中存储智能体的约束、先前决策、阶段性结果、可用工具接口和运行规则。
  • 对于任意 Index 智能体，智能体返回的上下文包可能只包含检索到的上下文块，以及相应的文本块来源、相关性分数和可能生成的摘要。另一个独立的内部上下文包可以采用上文扁平的实时请求处理工作流，也可以采用 ReAct 风格的循环：反复检索、判断检索结果的相关性并重试，直到积累足够的上下文。

上下文包原则是一种规划方法：先定义上下文包，再选择数据库。先选择向量存储，再期望它能涵盖一切需求，是大多数“演示中有效、生产中失效”案例的根源。下面的四类形态体系可用于检查候选原语能否为任务提供所需的上下文包。

MCP 在检索系统中的定位

MCP 为检索系统提供了发现和调用外部上下文来源的一种边界。智能体仍需要运行时来决定何时检索、验证结果，并将结果与当前任务状态的其余部分组合起来。同一系统的其它部分可以通过其它边界传递： skills 封装可复用的能力说明，A2A 可以将工作路由给远程专家，而 UI 协议可以将生成的状态流式传回应用。

下图区分了这些边界。从左向右阅读，可了解 MCP 上下文输入和 A2A 任务交付；再从下向上阅读，可了解 skill 代理、运行时执行和生成的 UX。请选择与上下文包及其必须承载的系统状态相匹配的边界。

根据数据形态选择合适的检索原语

每种数据形态都需要相应的检索原语。如果选错路径，检索会不断返回看似合理的结果，却悄无声息地遗漏查询真正需要的信息，而且不会出现任何错误提醒您。下表列出了每种形态应使用的原语。

形态 示例 合适的原语
非结构化文本文档、文章、代码注释、文字记录稠密向量 + 交叉编码器重排序
层次化文档法律合同、技术手册、嵌套规范带父节点指针的树索引
结构化表格／受治理表格客户记录、财务账簿、HR 表构建在事实来源之上的语义层
关系／图组织结构图、代码依赖关系、知识图谱图遍历（Cypher、GraphQL、自定义方案）

非结构化文本示例让语料库依次经过检索和生成，最终得到有依据的答案。

每个请求都会经过相同的四个步骤：

  • 将查询嵌入为向量。
  • 在段落索引中搜索 top-K 个最近邻段落。
  • 将这些段落拼接到提示词中。
  • 根据这些段落生成有依据的答案。

管理其它原语的 Index 智能体大体采用相同的结构，只是搜索、嵌入和验证逻辑有所不同。因此，请大胆尝试更适合您数据的形态。

嵌入：构建其它一切的基础原语

每个面向非结构化文本的 Index 智能体都从同一种原语开始。嵌入是通过学习得到的一段文本的数值地址，即一个固定长度的向量；它在向量空间中的位置使语义相近的文本彼此接近。由此产生两个实际结果：

比较：对两个向量计算余弦相似度，只需一次点积和两个向量的模。

存储：向量索引按照文本在该空间中的位置进行组织，以便高效执行最近邻搜索。

两者都依赖同一种原语：嵌入模型。本课程通过 helpers.embed 路由嵌入调用，由它代理访问托管的 NVIDIA 嵌入 API 入口，因而所有内容都能在浏览器中运行，无需实验路径或本地服务器。

嵌入 API 契约。

嵌入 API 入口接收包含三个字段的 JSON 请求，并返回一个向量数组：

  • input 是待嵌入的文本批次，类型为 string[]。
  • model 指定嵌入模型，类型为 string。
  • input_type 的值为 "query" 或 "passage"。
  • 响应包含一个 data 数组，其中每个条目都包含类型为 embedding 的 number[]。

NVIDIA 嵌入模型会根据您传入的 input_type，为同一文本生成不同的向量。训练目标会让问题更接近能够回答它的段落，而不是仅仅重复其用词的文本，因此，对两个类型正确的输入计算余弦分数可以很好地反映相关性。如果使用 "passage" 类型嵌入查询，或反过来使用错误类型，评分函数会悄无声息地失效，召回率随之降低，但不会显示错误消息。

用三十行 top-K 余弦代码实现完整检索器

“向量数据库”只是为 Index 智能体已经完成的简单任务加了一层包装。它将每个段落与其嵌入一同存储，并根据余弦相似度，为任意查询嵌入返回最接近的 top-K 个段落。在浏览器中，只需三十行 JavaScript 即可实现。

下面的单元将基于少量文档构建一个 Index 智能体，并对其执行查询。请编辑语料库和查询，然后观察哪些段落排到了最前面，并思考其中的原因。

故障模式：陈旧的嵌入。

向量索引是嵌入模型输出的缓存。生产系统必须防范以下几种特定故障：

  • 一旦更换嵌入模型，所有缓存向量都会失去意义，直到您重新嵌入每个段落。
  • 提供商悄悄升级模型，分数随之漂移，却不会触发任何错误。
  • 两个服务共享同一索引，却固定使用不同的模型 ID；该索引会向其中一个服务返回毫无意义的结果。

可靠的索引会为每个缓存向量同时固定嵌入模型 ID，并拒绝混用不同版本。本课程的规范固定值是 nvidia/llama-nemotron-embed-1b-v2，通过课程托管在 build.nvidia.com 的代理提供服务。

搜索小文本块，返回其父文档

基础的 top-K Index 智能体需要权衡召回率与精确率，这不是任何嵌入模型能够解决的问题。您必须在短文本块和长文档之间做出选择：

  • 短文本块的嵌入更精准（向量表示的是一个聚焦的概念），但缺少上下文（仅凭一句话通常不足以作答）。
  • 长文档具有完整的上下文（每项事实都有其所属语境），但嵌入结果较为模糊（向量是许多观点的平均表示）。

生产环境通常采用两级索引。对小文本块进行嵌入，以保持检索精度；某个文本块匹配后，则返回其父文档，使模型仍能看到该文本块周围的完整上下文。

下面的练习使用三个父文档构建这种模式。每个文档都拆分为简短的句子块，查询则返回匹配的父文档。

将索引封装为由模型决定是否调用的工具

检索索引本身只会在收到查询时给出答案。将其封装为模型可选择调用的工具后，它便成为一个索引智能体，由模型判断是否值得执行检索。下面的单元格分五步实现这一过程：

  1. 语料库只需嵌入一次，并保存在内存索引中。
  2. 使用 JSON 模式声明一个 retrieve(question, k) 工具。
  3. 智能体接收用户的问题，并决定是否调用该工具。
  4. 如果调用，系统会在索引上执行余弦检索，并将 Top-K 段落作为工具消息追加到上下文中。
  5. 第二次调用 LLM，依据检索到的段落撰写最终答案。

您刚刚搭建的“将检索器用作工具”模式可直接扩展到生产环境。将内存中的余弦函数替换为服务器端的 FAISS+BM25+重排序工作流，只会改变执行器；工具模式、智能体循环和最终答案步骤均保持不变。

其它三种模式如何构建

您刚刚构建了从语料库到答案的非结构化文本路径。这里列出其它三种模式，帮助您在实际场景中识别它们并选用正确的基础技术。每种模式都有成熟的生产实现方式，概要如下。

  • 层次化文档。使用保留标题层级的文本分块器，并结合原子化表格提取、父级指针以及用于结构搜索和语义搜索的双索引。为提高召回率，对小型子文本块建立索引；命中后获取其所属父级内容，使模型能够同时阅读匹配的条款及其所在章节。
  • 面向图形和图表的页面图像检索。采用双向量配置，同时嵌入渲染后的页面图像及其文本，使查询在答案位于图形或幻灯片中时也能将其检索出来。
  • 结构化表格与受治理表格。本课程不构建此模式。标准的生产模式是在智能体和行级数据之间设置语义层，仅公开该数据包所需的精选指标。
  • 关系数据与图数据。智能体调用图遍历工具（Cypher、GraphQL 或自定义工具），而不是向量存储。返回的数据包是一个子图，其中的显式边会随数据一起进入提示词，从而将实体间的关系完整传递给模型。

当 Top-K 并不适用时：GraphRAG 与全局问题

本页介绍的每种检索器都用于回答局部问题。这类问题的答案存在于少量段落中，Top-K 相似度检索可以找到这些段落供模型阅读，例如询问合同对终止事项有何规定，或哪篇论文提出了 HyDE。另一类问题的答案根本不存在于任何单独段落中。例如，询问一千份文档的主要主题时，答案过于分散，不会存在于某个段落里，只有从整个语料库中才能归纳出来。

Top-K 只返回三个最佳匹配项，因此模型只会总结这三个文本块，完全看不到语料库中的其它九百九十七个段落。GraphRAG（Edge et al. 2024）并不提高 K，而是改变问题的处理方式。它会在建立索引时预先投入一次 LLM，以便：

  • 读取语料库，将实体及其相互关系提取到知识图谱中；
  • 检测图中的社区，即由紧密连接的实体组成的集群；
  • 分别总结每个社区。

随后，在查询时通过汇总相关社区的摘要来回答全局问题，再将这些局部答案归并为一个答案。这个过程是在结构上执行 MapReduce，而不是按相似度进行查找。

下面的单元格通过一个小型语料库具体展示两者的差异，并运行真实工作流，而不是回放预设脚本。它以两种方式提出同一个全局问题：普通 Top-K 检索，以及 GraphRAG 针对命名社区执行的 MapReduce。请观察 Top-K 如何依据偶然匹配问题用词的文本块作答，而社区处理方式如何还原整个语料库的共同主题。修改语料库、社区或问题，然后再次运行。

在冻结模型前设置 Top-K 检索器，可以很好地回答局部问题，却完全无法回答全局问题。将语料库重组为带摘要的社区后，便能获得全局答案，代价是执行一次成本高昂的索引构建。

继续学习之前

  1. 第 4 部分中的余弦方法以相同方式计算任意两个向量的得分，不考虑哪个向量是查询；但此处使用的 NVIDIA 嵌入模型会通过 input_type 区分查询和段落。这种非对称性提供了哪些纯余弦方法无法提供的能力？
  2. 构建索引时会对语料库中的每个段落嵌入一次，而在线处理路径会嵌入每个新问题。哪些更改需要完整地重建索引，哪些更改只需生成一个新的查询嵌入？
  3. Top-K 始终返回 K 个段落，即使所有得分都很低。在允许这些段落进入提示词之前，智能体应检查什么信号？

参考资料

  • Lewis et al., Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks (NeurIPS 2020)。这篇论文奠定了先检索、后生成的经典范式；上图根据该论文重新绘制。
  • Karpukhin et al., Dense Passage Retrieval (EMNLP 2020)。该论文提出的双编码器结构是查询/段落嵌入非对称性的基础，此处的 NVIDIA 嵌入模型会执行这种区分。
  • Johnson, Douze & Jégou, Billion-scale similarity search with GPUs (FAISS, 2017)。您所了解的每种“向量数据库”都采用了这种向量索引数据结构。
  • Gao et al., HyDE: Precise Zero-Shot Dense Retrieval without Relevance Labels (2022)。该方法生成一个假设答案并嵌入该答案，而不是直接嵌入问题；对于简短或含义模糊的查询，通常能快速取得成效。
  • Lin et al., Pretrained Transformers for Text Ranking (2020)。生产级检索技术栈在第二阶段采用的重排序器模式。
  • Edge et al., From Local to Global: A Graph RAG Approach to Query-Focused Summarization (2024)。该方法构建由 LLM 派生的知识图谱，并预先总结其中的社区，以便回答覆盖整个语料库的全局问题；上方的工作流图根据该论文重新绘制。
