OpenShell 沙盒

模块 3 为 OpenClaw 提供了持久上下文和无人值守触发器。提示词规则和工具框架检查仍会影响它尝试执行的操作，而 OpenShell 则将最终的允许或拒绝决定置于智能体无法改写的沙盒中。

本页中，您会向本地 OpenClaw sandbox 发送真实命令，查看每条判定，并追溯产生该判定的规则。然后，您将检查第二层边界：sandbox 之上的 operator 控制平面。

在追踪策略执行过程时，请区分这三种产品的角色。
  • OpenClaw 是智能体框架。它决定使用哪个工具以及尝试执行什么操作。
  • OpenShell 是安全运行时。它限制该操作能够访问的文件和网络目标，以及能够执行的操作系统操作。
  • NemoClaw 是参考技术栈，将 OpenClaw 和 OpenShell 与生命周期命令、策略预设、推理指南及部署默认配置封装在一起。

OpenShell 与具体智能体无关。同一道边界可以封装 OpenClaw、 Hermes、 LangChain deepagents，或其它需要操作系统级隔离的进程。

各防御层在何处介入

假设不受信任的内容指示智能体读取凭据并将其发送出去。三个不同层级都有机会阻止该操作，且每一层要回答的问题各不相同。

  • 提示词塑造意图。 “不得泄露凭据”之类的规则会告诉模型应如何行事。但模型仍可能被对抗性检索内容、恶意工具输出或循环中的其它智能体欺骗。此层会影响决策，但智能体仍保留运行时授予它的所有权限。
  • 智能体工具框架验证请求。 OpenClaw 或 Hermes 可以在请求到达操作系统前，拒绝不受支持的 shell 形式、被禁止的工具调用或格式错误的参数。这种确定性检查很有用，但它仍属于应用逻辑，可能存在配置错误、版本过时或遭到入侵的问题。
  • 沙盒限制操作结果。 OpenShell 仅向进程授予策略允许的权限。即使提示词和工具框架均未能阻止操作，操作系统仍可在文件、网络或进程操作完成前将其拒绝。

本页的实际操作将评估最后一层防御。您将尝试执行一项操作，观察允许或拒绝的判定，并将该判定与执行它的机制对应起来。

为什么策略执行应位于模型之下

假定看似有效的请求仍可能造成危害

零信任拒绝仅根据请求来源对其给予隐式信任。 OWASP 的提示词注入指南将同样的原则应用于智能体：约束工具、限制权限，并假定外部内容可能引导模型。

仅授予任务所需的权限

Saltzer 和 Schroeder 将此描述为最小权限原则：每个组件只获得完成其工作所需的权限。由于这一原则早于智能体出现，因此可以自然地应用于当前场景。

评估边界，而非尝试证明意图

Rice 定理排除了对任意程序的非平凡行为进行通用判定的可能性。对于具备代码执行能力的智能体，同样应保持谨慎：应对运行内容周围的边界进行检测，而不能假定静态检查能够证明未来的每项操作都安全。

沙盒机制如何回答可测试的问题

本地 OpenClaw sandbox 结合了四种操作系统机制。每种机制都回答一个可以实际验证的问题，它们共同在多个边界上执行策略。请先阅读本页后面的实时策略，再判断其中任何一项保证是否普遍适用。

1 · 此进程可以连接到哪里？

网络命名空间（netns）为智能体提供隔离的网络栈。初始状态下，出站访问处于关闭状态。 HTTP CONNECT 代理是唯一的出站路径。 Open Policy Agent（OPA）会依据策略检查发起请求的二进制文件、主机、端口和路径。策略的编辑者决定允许哪些连接。

2 · 它可以访问哪些文件？

Landlock 是一种限制后续文件系统访问的 Linux 安全模块。在此处，它将新的文件操作限制在策略授予的路径内。这是一种强制执行机制，但仍需考虑兼容模式、OverlayFS，以及施加限制前已打开的句柄。请阅读实时策略，并测试您打算暴露的路径。

3 · 它可以请求哪些内核操作？

系统调用（即 syscall）用于请求 Linux 内核执行操作。seccomp 是 Linux 系统调用过滤机制；其 BPF 过滤器会对照允许列表检查每个请求。被拒绝的调用会在操作执行前返回 EPERM，表示“操作不被允许”。此本地 OpenClaw sandbox 会排除 ptrace、mount 和 setuid 等危险原语。

4 · 它最初拥有多大权限？

智能体以非 root 进程的身份运行，使用无特权的 sandbox 用户。因此，即使攻击成功，最初获得的权限也较少。较低的初始权限可以缩小影响范围，但不能证明权限提升不可能发生。主机、容器配置和系统调用策略仍是安全边界的一部分。

进一步探索：完整轨迹

真实的智能体会串联多条命令，以实现上方任何单个独立单元都未曾尝试过的目标。请在下方框中描述一个此类目标。智能体会先规划为实现该目标而要运行的完整 shell 命令序列，再在沙箱中逐条运行命令并显示结果。请留意这份计划：内核会在其中某一步拒绝继续执行，因为您之前加固的隔离机制会立即阻断这条失控轨迹。

单条命令中的一项规则在这里仍然适用：任何步骤一旦打印出秘密，该秘密就已经泄露，即使后续步骤的出站访问被拒绝也无济于事。看到这种情况后，请编辑目标或规划提示词，再对这条轨迹进行更深入的探索。

证明沙箱的约束边界，再通过实时运行确认

您无需盲目信任稳健性声明。openshell policy prove 命令会检查策略属性，若属性不成立则返回反例；与此同时，代理会对每个连接做出确定性的允许或拒绝判定。您将在浏览器中根据本地 OpenClaw sandbox 的真实策略计算同一判定，再在实时 sandbox 中执行该操作，并确认内核判定是否与预测一致。

下方的策略测试会检验二进制程序身份。策略按程序而不是按主机授予出站权限，因此代理在查看连接目标之前，总会先检查是哪个二进制程序打开了连接。所以，openclaw 等获准程序可以访问推理 API 入口，而临时使用的 curl 访问完全相同的 API 入口时会被拒绝。从下方按钮中选择任意操作，即可立即看到其静态判定；推理-API 入口操作最清楚地展示了这种同一主机、不同结果的变化。

每个结果都是真实的内核判定。每条流程的实时部分都会通过 openshell sandbox exec，在您于 Kickstart 中连接的本地 OpenClaw sandbox 上运行，因此返回的每个结果都是内核在线路上做出的实际判定。请在另一个标签页中保持本地 OpenClaw sandbox 打开，使其访问会话保持有效。
如果预测判定与实时结果一致，就说明该实例执行的策略与静态分析的预测相符。如果二者不一致，则说明实例的行为未被预测涵盖：可能有人在您不知情的情况下添加了预设，也可能实例确实存在静态视图未能发现的缺口。无论是哪种情况，您都能在真正开始信任该实例之前获得重要信息。

沙箱之上：控制平面

到目前为止，衡量的都是智能体能做什么，但更重要的问题是：谁能通过智能体上方的平面重新配置它。访问该平面的方式因系统而异。在此实例中，该平面是一个网关；可以使用模块 3 中的同一个 OPENCLAW_GATEWAY_TOKEN，以 operator.admin 作用域访问它，而这些操作完全不会经过沙箱。

这一项凭据可以访问：

  • 使用 agents.files.get，并直接从磁盘设置角色设定文件（SOUL.md、AGENTS.md）。
  • 使用 cron.add 和 cron.list 管理在对话结束很久后仍会触发的计划任务。
  • 使用 config.get 和 config.patch 管理完整的智能体配置：模型、工具，甚至 toolSearch。
  • 使用 chat.send 在任务进行期间发送消息，使智能体改换方向，同时表面上看起来仍在执行任务。
  • 使用 sessions.reset 和 delete 清除其记忆；使用 gateway.restart.request 重启运行时。

这些调用串联起来就会形成一条权限提升路径。攻击者读取角色设定后，可以植入一个在对话结束很久后才触发的 cron 任务，再对正在使用的配置执行 patch，扩大智能体可以执行的操作范围。任务进行期间插入的一轮消息会改变其方向，而重启运行时则会让新配置正式生效。

您在上文加固的沙箱管控智能体的系统调用，但这些操作都不是由智能体发起的系统调用。实例本身有多坚固与控制平面能触及多大范围是两个独立的问题，而团队经常严密封锁前者，却让后者门户大开。

此处的保护刻意只覆盖一侧：沙箱能够有效抵御智能体自身的错误，甚至能抵御智能体遭入侵后的行为，但对于持有其上层控制平面权限的人，沙箱完全无从感知。您应当像保护 root 权限一样谨慎地保护该平面的访问权限，因为在此实例上，它可以完全绕过沙箱的所有检查，重新配置智能体的身份和计划任务。

针对您自己的本地 OpenClaw sandbox 进行枚举。此单元只读取数据，因此只会测量可访问范围，不会更改任何内容。

沙箱无法拦截的风险

到目前为止，涉及的都是智能体自身的操作，内核也守住了边界。但仍有两类截然不同的危害可以绕过它。第一类来自您刚刚枚举的控制平面，它能从检查点上方重新配置智能体。第二类则藏在获授权的行为范围内：其中每项操作都获准执行，真正的危害来自这些操作组合在一起的方式。

不可信输入、私有数据和外部通信共同构成致命三要素。

  • 私有数据是指智能体可以读取、但不应泄露的任何内容：工作区文件、电子邮件、token、记忆或内部记录。
  • 不可信输入是指并非由 operator 作者编写、但模型仍可能将其视为指令的外部内容，例如网页、议题、文档、工具结果或对等智能体的响应。
  • 外部通信是指任何能够将字节传出的路径：HTTP、拉取请求、聊天、日志行、图像加载，甚至是用户可能点击的链接。

当这些权限组合在一起时，风险便会出现。策略可以正确地只允许一个出站 API 入口，但该入口仍是全双工的：请求会发出，响应又会作为更多输入返回。一旦恶意内容能够操纵模型，就可以要求模型读取私有数据，再通过 sandbox 视为允许的通道发送这些数据。只要在 sandbox 之上的任意一段进行管控，就能切断漏洞利用所需的路径。

这些缺口在默认实例上确实存在，并且网络和文件系统策略都无法判定它们：

  • 篡改角色设定。 SOUL.md 可写且归智能体所有，因此发生混乱或遭到入侵的智能体可以改写自己的身份设定。所有者可以撤销 chmod 锁定；只有从沙箱外部以 root 设置的 chattr +i 才能保持有效。
  • 控制平面触及身份层级。任何能够打开它的人（在此实例上，即 OPENCLAW_GATEWAY_TOKEN 的持有者）都可以读取角色设定、植入 cron 任务并注入一轮消息；这些操作全都发生在检查点上方，内核永远无法看到。
  • 入站注入。默认拒绝的出站策略可以阻止数据外泄，却无法阻止对抗性指令通过获授权的通道进入，也就是 Greshake et al.所命名的间接提示词注入。要发现这种攻击，需要在更高层进行输入分类或建立行为基线。
  • 通过获准通道外泄。获准的 API 入口可能成为数据外泄的路径。策略只能证明该通道已获允许，无法判断其中传输的字节是否无害。
  • 隐藏意图。网关在转发操作时会剥离模型的推理过程，因此潜伏型智能体可以在获授权策略范围内执行有害工作流，而其中任何单项操作看起来都没有问题。
  • 维护同伴。在智能体集群中，负责评估或确认对等智能体关闭状态的智能体，会因社会情境而改变判定。只有行为回归测试才能发现这种情况。

根据故障模式选择控制措施

沙箱限制遭入侵的进程能够访问的范围。对于内核无法理解其含义的决策，仍需由应用和运维实践负责。

记忆或上下文污染当策略将指定文件设为只读时，可以保护这些文件写入来源追踪、可审查的历史记录、信任标签，以及从已知良好状态恢复

这些类别与 OWASP Top 10 for Agentic Applications 一致。请使用此表选择策略执行点，不要要求单一层识别所有类型的危害。

沙箱建立的是安全底线，而非完整的防御体系。相应的实践是：仅向智能体授予满足需要的最小活动范围，证明该范围能够提供哪些保证，并在其上层配备相应机制，以应对任何证明都无法覆盖的故障。
