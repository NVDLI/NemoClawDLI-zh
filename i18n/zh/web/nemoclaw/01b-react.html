ReAct 循环

基于语言模型构建的智能体与其它系统一样，运行“感知—推理—行动”循环。但其中有一个细节赋予了这一模式名称：模型会在每次行动之间用文字进行推理。 Yao et al. (2022) 将这种结合推理与行动的模式称为 ReAct。他们发现，将简短的推理轨迹与工具使用交替进行，在许多任务上比预先规划全部步骤或不经推理直接行动更可靠。

工具是运行框架可代模型执行的代码：一个具有名称、描述、输入模式和返回值的函数。工具调用是模型发出的结构化代码执行请求。运行框架解析该请求、执行函数、追加结果，然后再次调用模型。

大多数通用智能体框架都以这一循环为基础，LangChain 的 createReactAgent 也是如此。本模块的后续内容将逐步构建这一循环。

决定循环下一步操作的唯一字段

每个聊天补全响应都包含一个 finish_reason 字段，用于说明模型停止生成的原因。在智能体循环中，您只需依据这一信号决定下一步操作：运行工具、向用户返回答案或处理错误。在了解各个字段值的含义之前，请先发起两次调用并观察该字段的变化。

第一次调用由模型自行作答，返回了 "stop"。第二次调用向模型提供了工具，并要求获取训练数据无法提供的信息，因此它没有停止，而是返回 "tool_calls"，将需要运行的函数名称交给代码。这两个值涵盖了常见的分支情况。其余值表示发生了问题，循环会转入后备运行框架；智能体可以在其中重试调用，或将对话转交给人工处理。

  • "stop" 表示模型已生成最终答案，循环可以将 content 返回给用户。
  • "tool_calls" 表示模型要求代码运行指定函数，追加结果后再回调模型。
  • "length" 表示答案尚未生成完毕，token 预算就已耗尽。
  • "content_filter" 表示安全分类器停止了输出。

在现代 ReAct 中，一个简短的路由逻辑会读取该字段。如果模型请求使用工具，路由逻辑就会运行函数、追加结果并再次调用模型。如果模型已经停止，路由逻辑就会返回答案。

这种设计的优势在于，模型从不受最初计划的束缚。每当工具返回意料之外的结果时，该结果都会进入下一轮推理，模型可以重新评估当前状况，再决定下一步操作。

LLM 智能体的组成部分

仔细观察智能体，您会看到 Lilian Weng 在 2023 年提出的组成结构。语言模型位于中心，周围是记忆、规划、工具以及触达外部世界的行动。

本课程的最小智能体使用能满足需求的最简单方式实现每个部分：

  • 记忆是 messages[] 数组。
  • 规划是 finish_reason 路由逻辑。
  • 工具是运行框架公开的函数。
  • 行动是运行框架执行的工具调用。

这些都不在模型内部，而是您围绕一次文本输入、文本输出调用构建的运行框架。

这些模块彼此独立。可以单独替换模型、工具或路由；只要各模块仍遵守其它模块所依赖的契约，循环的其余部分就能继续运行。

阅读并非由您编写的智能体代码时，这种独立性同样重要。无论外层采用什么框架，任何基于 LLM 的智能体都必须包含以下四个部分；一旦出现故障，原因通常就在其中之一：

  • 模型返回了错误的 finish_reason；
  • messages 数组中缺少一轮消息；
  • 工具执行器返回了意外的值；
  • 或者路由误读了信号。

无论外围代码采用何种组织方式，这个四部分框架都能为您提供一份通用检查清单。

使用一个工具从头构建循环

整个流程很短：模型请求使用工具，执行器将时间戳追加为一条 tool 角色消息，模型读取该时间戳；当 finish_reason 的值为 "stop" 时，循环退出。

刚才 messages 数组内部发生了什么。
循环向 state.messages 中加入了四项：
  • 系统提示词（第 0 轮），
  • 用户的问题（第 1 轮），
  • 一条带有 tool_calls 字段的 assistant 消息（第 2 轮，即请求），
  • 以及一条保存函数返回值的 tool 角色消息（第 3 轮）。
第二次 LLM 调用读取了这四项，包括新增的工具结果，然后生成最终答案。这个不断增长的数组就是该智能体拥有的全部“记忆”。如果您将该数组保存到磁盘，并在下周重新加载，模型会继续对话，甚至不会察觉中间曾中断过。

上下文退化：循环越长，为何理解效果越差

随着上下文增长，这个问题更容易出现。上下文退化是指矛盾、过时的观察结果和不良约定不断积累在提示词历史中，最终导致模型下一次决策质量下降的趋势。这种影响还与信息所在的位置有关：Liu et al. (2023)的研究表明，模型可能无法充分利用埋藏在长上下文中部的信息。重要信号距离当前轮次越远，循环就越容易忽略它或产生与之矛盾的结果。

常见的缓解方法会让每次决策尽量靠近其所需的证据：

  • 在循环积累观察结果之前先制定计划；
  • 委派子任务，让每个子智能体在较短的上下文中工作；
  • 或者在早期轮次成为负担之前对其进行总结。

每种方法都会在延迟、保真度或复杂度方面付出代价，因此都需要结合当前任务权衡取舍。

使用预构建的相同循环读取本课程

上面的循环硬编码了一个很小的工具。LangChain 的 createReactAgent 对相同机制进行了泛化，可支持更多工具、标准接口和可观测性集成。下方的课程实例只接入了一个工具 read_course_page，它可以将本课程任意页面以 markdown 格式提供给智能体。模型会根据问题决定读取哪些页面，请亲自试一试。

该单元格会生成一个制品。运行后，您得到的不是满屏日志，而是由智能体自身代码渲染、可与之对话的聊天面板。“制品”一词早在当前用法出现前就已存在，因为构建工作流和机器学习训练运行多年来一直会生成“制品”和“模型制品”。Anthropic 最近推出的 live artifacts 进一步明确了这一概念在智能体领域中的含义：制品是由智能体构建、可持久使用的 HTML 交互界面；即使生成它的回复早已结束，您仍可继续使用。下方面板以较小规模构建了一个这样的制品。智能体不仅能返回纯文本，还能交付完整界面；这一主题将贯穿本课程的后续内容。

运行单元格构建面板，然后与它对话。可以使用 Pages 标签固定一个或多个页面，使每个答案都以这些页面为依据；也可以不固定任何页面，让智能体自行选择要读取的内容。回复会渲染为 markdown，并为智能体读取的每个来源显示一个标签；展开标签即可查看它检索到的文本。除答案外，您还会看到推理轨迹和 token 使用情况。它会分别记住每个聊天中的对话。编辑单元格并重新运行即可重建制品。

继续学习之前

编辑上方画布中的输入并重新运行，即可回答以下每个问题。

  1. 即使模型不需要使用工具，也强制它进行工具调用。尝试提出一个工具确实无法回答的问题（“法国的首都是哪里？”），并观察第 1 步中的 finish_reason。它的值是 "stop" 还是 "tool_calls"？现在编辑系统提示词，要求模型必须先进行工具调用再回答（“您必须始终调用 get_current_time 一次，然后再回答。”）。模型是否遵从了要求？如果模型根据训练数据对另一个答案方向很有信心，这一现象说明系统提示词对模型的引导作用有多强？
  2. 针对一个确实需要工具的问题统计执行步数。 “距离 UTC 17:00 还有多少分钟？”需要进行多次工具调用。多运行几次。模型调用了 get_current_time 一次、两次还是三次？为什么模型会再次调用已经取得输出的工具？您会如何在系统提示词中抑制这种行为？
