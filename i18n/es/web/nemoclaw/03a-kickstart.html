Conecte el stack de NemoClaw

En los Módulos 1 y 2, la orquestación permaneció en el navegador. Un flujo de trabajo terminaba cuando la página dejaba de transportar sus mensajes, resultados intermedios o el estado de sus ramas. El Módulo 3 lleva los mismos patrones de agentes a un launchable de NemoClaw en Brev. OpenClaw conserva el historial de la sesión y un workspace respaldado por archivos, sin dejar de ofrecer herramientas; OpenShell limita lo que ese agente en ejecución puede alcanzar. Desde el navegador, comparará la API de modelos sin estado con el gateway persistente de OpenClaw.

El diagrama recorre ese espectro de izquierda a derecha:

  • Endpoints HTTP REST. El modelo responde a cada llamada de forma aislada: en Chat Completions API, su código transporta el historial; en Responses API, el servidor puede conservarlo.
  • Model Context Protocol (MCP). Un protocolo estándar permite al runtime acceder a herramientas sin escribir una integración específica para cada una.
  • Gateway persistente. OpenClaw mantiene un /cli/gateway WebSocket abierto y transmite eventos por JSON-RPC, en lugar de responder a una solicitud por vez.

Los dos endpoints que usará a partir de ahora

El endpoint del modelo responde mediante la misma API que utilizó antes. El gateway del launchable llega a un proceso de OpenClaw que conserva sesiones y puede ejecutar herramientas. El código de soporte para los protocolos permanece disponible en las celdas; siga principalmente el endpoint, la credencial y el límite de estado de cada interfaz.

build.nvidia.com

Inicie NemoClaw en Brev

La configuración crea un launchable que ejecuta OpenClaw dentro de OpenShell en https://nemoclaw-<id>.brevlab.com. La identidad, las herramientas, la memoria de sesión y la política del sandbox residen allí. El navegador llega al agente mediante el gateway WebSocket en /cli/gateway. Para una implementación local, siga el playbook de configuración de NemoClaw y mantenga el mismo límite de conexión.

Autenticación mediante token del gateway. Sesiones mediante x-openclaw-session-key.

Paso 1 · Pruebe los endpoints

Los widgets siguientes envían una solicitud breve a cada endpoint y muestran la respuesta. Verde significa que está listo.

Latencia y tiempo hasta el primer token por modelo

Antes de elegir un modelo, mídalo. Las celdas siguientes obtienen del catálogo los modelos coincidentes, transmiten el mismo prompt breve a cada uno y registran el tiempo hasta el primer token (TTFT) y el tiempo total. La celda que consulta el catálogo comienza abierta para mostrar el filtro antes de ejecutar el benchmark.

Si la sonda de OpenClaw agota el tiempo de espera o devuelve 502. Es probable que el entorno de ejecución del agente aún esté arrancando: el launchable puede haberse iniciado antes de que OpenClaw terminara de cargar su política YAML. Espere 30 segundos y vuelva a ejecutar la sonda. Si sigue sin responder, utilice la celda Recuperar en la sección del gateway antes de continuar.

La solicitud de la sonda como código editable

Esta celda realiza la misma llamada que la sonda, con el código a la vista. Reutiliza la URL, el token y el JWT de Cloudflare que guardó la sonda. Edite PATH, METHOD y BODY para enviar otras solicitudes. El estado, los encabezados y el cuerpo aparecen debajo.

TRANSPORT controla cómo llega la credencial al launchable:

  • "proxy" dirige la llamada por el worker de CORS y envía el JWT de Cloudflare Access en un encabezado.
  • "direct" llama al origen del launchable con credentials: "include" y sin JWT, apoyándose en la cookie de Cloudflare Access que ya posee el navegador.

En un curso alojado por separado en Pages, el modo directo depende de una cookie válida del launchable y de su política de respuesta entre orígenes; la ruta con JWT explícito usa el relay. Cuando el curso se incorpora al mismo launchable de NemoClaw que ejecuta el runtime, el modo directo utiliza el mismo origen y no necesita el relay.

Paso 2 · El gateway

El endpoint del modelo utiliza Chat Completions API, donde un solo POST contiene todo lo que necesita la llamada.

  • La línea de solicitud es un único POST a la ruta de completions.
  • El cuerpo JSON transporta model y messages.
  • Un encabezado Authorization identifica al solicitante.

OpenClaw también implementa esa ruta internamente, pero esta página no puede alcanzarla porque la capa de Cloudflare Access del launchable bloquea el acceso desde el navegador.

El canal que sí está disponible utiliza otro protocolo: un WebSocket en /cli/gateway que habla JSON-RPC.

La interfaz de control de la pestaña del navegador no utiliza un canal privado especial. Se comunica con el agente mediante el mismo WebSocket en /cli/gateway que usted puede usar, y la única credencial necesaria es el token del gateway. La sonda descubre ese token para que no tenga que pegarlo. Una solicitud GET /api/agent, autorizada por su sesión de Cloudflare Access, lo devuelve en agent.dashboardUrl. Deje el campo vacío para que la sonda lo complete.

Ese token posee el alcance operator.admin, la misma autoridad que la interfaz de control. Con él puede:

  • models.list enumera todos los modelos que ofrece el runtime.
  • cron.add programa trabajo que se ejecuta sin su intervención.
  • chat.send con una sessionKey envía un mensaje directamente al ciclo del agente.

Primero, prepare un launchable nuevo

Un launchable nuevo de NemoClaw viene con tools.toolSearch activado. En un modelo más débil, esta opción puede impedir el uso correcto de herramientas:

  • Síntoma: solicita un comando, no llega ninguna respuesta, la ejecución se detiene y termina por agotar el tiempo de espera.
  • Causa: toolSearch permite que el modelo acceda a herramientas escribiendo código para un puente (tool_search_code · “run bridge code”). El modelo débil puede quedar atrapado en ese puente en lugar de llamar exec.
  • Solución: ejecute la comprobación de estado. Si toolSearch está activado, la celda Recuperar lo desactiva con config.patch y reinicia el runtime. Hágalo una vez por cada instancia nueva.

Con el runtime preparado, puede enviar un mensaje al ciclo del agente. Ejecute las tres celdas siguientes en orden: las primeras conectan y enumeran modelos y tareas cron; una celda posterior envía un turno de chat; la última transmite la traza. Lea la traza fila por fila:

  • Cada fila ⚙️ es una llamada a herramienta con sus argumentos de entrada.
  • Cada fila ✓/✗ es el resultado de esa herramienta.
  • El gateway no reenvía el razonamiento del modelo, por lo que esta traza de entrada y salida ofrece la vista por pasos más detallada. Cuando una ejecución se detenga sin resultado, use la celda de logs anterior para seguir el runtime.

Cada ejecución de chat comprueba su estado. Si aparece ⚠ DEGRADED, vuelva aquí, ejecute Recuperar y repita el intento.

Quien pueda leer el entorno del launchable también puede leer ese token; quien posea el token es un operador con todas las capacidades anteriores. El Módulo 4 convierte esta comodidad en la pregunta central de seguridad.

Paso 3 · La memoria vive en la clave de la sesión

Cada chat.send recibe una sessionKey, que determina lo que el turno recuerda:

  • La misma clave, dos veces: el gateway rehidrata el historial del primer turno antes de ejecutar el segundo, por lo que el agente responde a partir de una conversación que el cliente nunca volvió a enviar.
  • Una clave distinta: comienza desde cero, sin conservar nada.

La primera celda registra un dato y después lo solicita con la misma clave. El agente utiliza un turno que el cliente no volvió a enviar porque el gateway rehidrató el historial en el servidor. Las otras dos celdas permiten administrar ese estado almacenado.

  • Limpiar borra una sesión con una sola llamada; el turno siguiente comienza sin historial. Cada celda de chat también contiene una línea sessions.reset comentada para reiniciar allí mismo.
  • Limpiar sesiones elimina las sesiones desechables acumuladas durante las pruebas, incluidas las claves por ejecución del Paso 2, y conserva únicamente la sesión principal.
La clave de sesión es la única identificación de la conversación enviada por el cliente. A partir de ella, la pasarela recupera en el servidor toda la sesión antes de cada llamada; el cliente no necesita reenviar la transcripción. Dos claves diferentes siempre identifican sesiones separadas, aunque las conversaciones tengan contenido idéntico.
